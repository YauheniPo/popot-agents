Поведение и границы подхода

Что теряется при удалении Task?

История остаётся. Прежний workspace и память процесса в новую среду не переносятся. Snapshot связан с actor и удаляется при очистке. Важные файлы нужно сохранять отдельно: git, внешние артефакты или другое долговечное хранилище.

Почему DATA, а не память процесса?

snapshot_mode: data в ax_local/config.json сохраняет файлы и использует COLD_BOOT: новый Python получает восстановленный диалог. FULL и golden restore на локальном ARM64 воспроизвели illegal instruction. FULL остаётся явной настройкой для проверенного runtime. Фоновые процессы в DATA не продолжаются.

Что произойдёт при ошибке snapshot?

При ошибке resume API сообщает код 503, MCP возвращает ошибку инструмента, а статус чата становится resume_failed. Task, checkpoint и слот сохраняются для повтора с тем же sessionId. При неподтверждённом suspend ответ остаётся успешным, статус — snapshot_unconfirmed: наличие нового snapshot и освобождение ресурсов ещё не подтверждены. Обычный срок хранения Task продолжает действовать.

Как не раздувать snapshot?

Рабочий код и нужные между ходами файлы храните в /workspace. Временные файлы и фрагменты передачи истории — в /tmp: DATA их не сохраняет. Зависимости, нужные при каждом старте, лучше включать в worker image. HOME и cache сейчас находятся в workspace, поэтому их размер также влияет на snapshot. Важные результаты сохраняйте в git или внешние артефакты до удаления Task.

Где видны время и проверка snapshot?

События snapshot_saved и snapshot_restored передают mode и elapsed_seconds. Они доступны в последних событиях MCP activity и в уведомлениях при включённом progress. Длительность включает ожидание готовности; для DATA resume — также запуск harness и загрузку диалога. Локальный lifecycle-тест проверяет три цикла resume, историю, SHA-256 файла 1 MiB и передачу длинного диалога без вызова модели. Время зависит от размера данных и нагрузки.

Как работают роль и инструменты?

Код harness уже в готовом образе. При создании сессии он получает инструкции роли, skill references, tools, mcpServers и allowed_roles. Pod не перенастраивается навсегда. Локальные shell / file / MCP-процессы запускаются с UID/GID 10001.

Что передаётся дочернему агенту?

Текст задачи, оригинальные запросы и ограничения пользователя, непроверенный последний ответ родителя и политика публикации. Файлы и tool evidence не копируются автоматически: нужны явные данные или доступный repository/ref/PR.

Как защищается делегирование?

Проверяются allowed_roles, срок родительского хода, глубина, количество вызовов и циклы. messageId дедуплицирует повтор отправки. Ошибка, пустой или обрезанный ответ дочернего агента не считаются успешным результатом. После ответа/ошибки дочерний Task закрывается; незавершённые потомки отменяются при завершении хода родителя.

Может ли успех одной подзадачи скрыть ошибку другой?

Ошибки учитываются по паре «роль + текст подзадачи». Если qa_engineer не смог проверить API, успешная проверка UI той же ролью не закрывает эту ошибку. Её снимает успешный повтор той же подзадачи. Незавершённая работа не должна превращаться в ответ «всё выполнено».

Что происходит после перезапуска API?

При штатной остановке API его Task удаляются; при следующем запуске также убираются оставшиеся старые Popot Task с недействительными proxy-токенами. Из PostgreSQL восстанавливаются диалог и роль, но прежний workspace не переносится в новую среду. Прерванные A2A-задачи отмечаются ошибкой. Очередь допуска была в памяти процесса: незапущенный запрос нужно повторить.

Есть ли другие способы запуска?

HTTP API, MCP, дочерний A2A-вызов и cron используют общий runner и очередь. Cron работает в AX API по UTC, создаёт отдельную сессию, сохраняет результат и удаляет её Task. Пропущенные во время выключения запуски не восполняются.

Почему Task называется popot-chat, если это review?

popot-chat-{sessionId} — общий префикс Task для сессий разных ролей, включая дочерние. Он не назначает роль chat и не означает отдельный пул chat-воркеров. Роль задаёт конфигурация сессии.

Как агент читает и сохраняет знания

Перед ходом HTTP harness делает recall: получает подходящие фрагменты текущего проекта вместе с источниками. Они добавляются как исторические данные с указанием проверить их по актуальным источникам.

После успешного ответа отдельный запрос к модели выделяет до пяти записей: решение, ограничение, факт, исправление или результат проверки. Runtime проверяет тип, источник и точное совпадение цитаты с наблюдавшимся evidence. Для фактов, исправлений и проверок требуется результат инструмента; сообщения пользователя могут подтверждать решения и ограничения.

В документ попадает текст записей. Исходная структурированная запись, включая дату, модель, ссылки и цитаты, сохраняется отдельно в external_metadata.popot_memory, формат v2. Эти служебные поля не передаются извлекателю сущностей. Полные диалоги и логи инструментов сюда не копируются.

Что означает memory_saved?

Запись принята сервисом, индексация запускается в фоне. Появление нового графа проверяется через memory_status. Ошибка памяти или исчерпание общего времени хода не отменяет готовый ответ; для неуспешного хода сохранения нет. Исторические записи всё равно требуют проверки: наличие цитаты не гарантирует истинность вывода.

Sources, доступ и хранение

popot-agents и github-yauhenipo-popot-bot-2-0 — два dataset / brain в одном Cognee. Source в интерфейсе выбирает проект, а не отдельный worker или сервер.

GitHub URL в задаче определяет github-<owner>-<repo>; другой проект задаётся маркером [project: popot-agents]. Продолжение наследует последний определённый проект из пользовательских сообщений. Без проекта или при неоднозначном выборе память пропускается. Дополнительный recall модели ограничен тем же проектом.

Нужны Cognee в конфигурации роли и доступ к сервису; cron_demo исключён. bash ax_local/up.sh запускает память через memory/up.sh и подключает её к сети kind. Оба подхода используют Compose-проект popot-memory с общими volumes.

Переживёт ли память удаление sandbox?

Да: документы, граф и векторы хранятся вне sandbox и RustFS, в volumes Cognee. Пересоздание контейнера и обычный docker compose down их сохраняют; удаление volumes стирает память. Файлы workspace и состояние процесса по этому механизму не восстанавливаются.

Какие вершины видны в графе

GLiNER извлекает сущности по project-ontology.ttl: проект, ПО, файл, pull request, именованная настройка и инженерное понятие. Связи: использует, входит в состав, изменяет и настраивает. Даты и безымянные количества не являются типами сущностей; важные числа остаются в тексте фактов.

Документы получают короткий заголовок из текста, фрагменты — Fragment · …, сводки — Summary · …. ID и связи сохраняются. В панели знаний доступны полный текст, ссылки и раскрываемые метаданные с доказательствами. Узлы Skills отражают импортированные навыки и сохраняются отдельно от фактов.

Почему граф может быть неполным?

Текущий gliner_demo и локальные embeddings не требуют платного ключа для индексации, но извлекатель может пропустить или неверно распознать сущность и связь. Исходный текст и доказательства доступны независимо от полноты графа. Извлечение кратких записей после ответа использует модель роли и её обычные лимиты.

Что делать со старыми memory_* документами?

memory/reindex.py переиндексирует старый формат по явно выбранным dataset. Сначала он сохраняет оригинальные документы и граф в приватный backup; изменения выполняются только с --apply. Запускайте при простаивающих агентах по инструкции памяти. Dataset и узлы Skills сохраняются; прошлые задачи автоматически не импортируются.

Что приходит клиенту во время работы

Когда включены уведомления MCP?

Укажите params._meta.progressToken в tools/call. Непустая строка или число, включая 0, включает notifications/progress. Если токена нет, он null или "", уведомлений не будет. Итоговый ответ и последние 20 событий в activity сохраняются.

Кто пишет пояснения и reasoning?

MCP пересылает JSON-события harness и runtime: запрос модели, ответ, вызов инструмента, его результат, делегирование. Заготовленных переводов в «агент сейчас делает…» нет. Параметры reasoning задаются в профиле модели; в прогресс попадают только поля reasoning, которые вернул провайдер. Текущий HTTP harness получает ответ модели целиком: это события, а не поток каждого токена.

Как виден прогресс дочернего агента?

Harness B → A2A в API → опрос GetTask родителем каждые 0,5 с → harness A → Popot API → MCP. События содержат agent_role. Используется A2A 1.0 через официальный SDK; собственный streaming A2A отключён.

Почему могут быть ping или пропуски событий?

: ping поддерживает SSE-соединение и не сообщает о работе агента. Он может остаться даже при отключённых progress-уведомлениях. A2A хранит до 64 событий, сейчас суммарно до 64 KiB и до 16 KiB на событие. При переполнении старые события удаляются, большие получают truncated и preview; приоритет отдаётся месту для итогового ответа. Это не полный журнал.

Общие CPU и память кластера

Графики показывают CPU в ядрах и memory working set: все pod и отдельно nodes с системными расходами. Эти линии нельзя складывать. Общие графики не меняются от фильтров namespace, pod, роли, задачи или процесса. Compose-сервисы за пределами kind в эти показатели не входят.

Роли, sandbox и отдельные процессы

По роли и Task фильтруются панели sandbox и процессов. В списках есть роли, работавшие в выбранный период, в том числе уже завершённые или приостановленные. Метрики общего worker pod или контейнера нельзя целиком приписать одной роли. Сумма RSS процессов может учитывать общие страницы памяти несколько раз.

Как собираются и хранятся данные?

CPU/RAM: cAdvisor → Prometheus раз в 15 с; kube-state-metrics добавляет состояние pod, requests и limits. Процессы sandbox: /proc → OTel Collector → Prometheus, сбор раз в 5 с только во время работы sandbox. При suspend текущие значения исчезают, история остаётся. Хранение на PVC ограничено 7 днями или 1 GB — что наступит раньше. Удаление kind-кластера удаляет локальное хранилище метрик.
