# Локальный вариант на AX

Эта папка запускает тот же HTTP harness и роли через AX `Task`, чтобы сравнить
его с Docker runner в текущей ветке. Исходный `compose.yaml` и Docker runner не
меняются. AX v0.3.1 и совместимый с ним Agent Substrate запускаются в
отдельном локальном кластере `kind-popot-ax` поверх Docker. Compose проект
`popot-ax-local` запускает PostgreSQL, AX API и MCP сервер. Для Claude и Codex
доступен `http://127.0.0.1:8003/mcp`; API на порту 8002 доступен только
контейнерам Compose.

## Где что находится

Поле `skills` в `config/roles.json` задаёт навыки роли, например
`["engineering/codebase-design", "engineering/tdd"]`. API проверяет пути,
а AX worker загружает выбранные Markdown-файлы в инструкции harness до
начала обслуживания сессии. Подробности и каталог: [skills/README.md](../skills/README.md).
После изменения навыков выполните `bash ax_local/rebuild-worker.sh` из корня
репозитория и начните новую сессию. В логах воркера появится `skills_loaded`.

| Путь | Назначение |
| --- | --- |
| `config.json`, `config.py` | Настройки AX и их проверка при загрузке. |
| `api/server.py` | HTTP API, роли и хранение сессий. |
| `api/ax_runner.py` | Создание AX Task и обмен сообщениями через `ax ssh`. |
| `api/provider_proxy.py` | Доступ Task к выбранному провайдеру без передачи его ключа в Task. |
| `api/delegation.py` | A2A-задачи, проверка разрешённых ролей, запуск и завершение дочерних агентов. |
| `api/cron.py` | Запуск задач ролей по cron в AX API. |
| `worker/delegation.py` | Инструмент `delegate_task` внутри AX harness. |
| `worker/` | Код, выполняемый внутри AX Task. |
| `cluster/` | Подготовка kubeconfig для API контейнера. |
| `cluster/controller_tools.*` | Локальная адаптация AX-контроллера для запуска инструментов с UID/GID 10001. |
| `docker/` | Dockerfile и списки файлов для сборки API и Task образов. |
| `tests/` | Локальные тесты AX варианта. |

`up.sh` — единая команда для первого и повторного запуска. Файлы `server.py` и
`container_kubeconfig.py` в корне папки сохраняют прежние команды как короткие
переходники к новым модулям.

Перед запуском API/MCP `up.sh` проверяет pod и реестр worker Substrate.
После перезапуска Docker/kind IP pod может измениться, а в реестре остаться
старым. Скрипт пересоздаёт только Ready pod с подтверждённым расхождением IP
и тем же UID, затем ждёт регистрации всех реплик WorkerPool с актуальными IP.
Исправные pod не перезапускаются. Такая же проверка есть в `rebuild-worker.sh`.
CLI проверки собирается один раз из закреплённой версии Substrate в `.local`.

После перезапуска Docker/kind выполняйте из корня репозитория:

```bash
bash ax_local/up.sh
```

Ожидание ограничено `ax.startup_timeout_seconds` (по умолчанию 300 секунд).
Если восстановление не завершилось, скрипт завершается с ошибкой до запуска
Compose API/MCP. Уже запущенные контейнеры Compose при этом не останавливаются.
Пересоздание неисправного worker прерывает задачи на нём; запускайте скрипт
до отправки новых запросов. Это проверка при запуске, а не постоянный монитор:
после следующего перезапуска кластера нужно снова выполнить `up.sh`.

По умолчанию используются `openrouter` и `openrouter/free` из
`ax_local/config.json`. Для смены модели или провайдера задайте
`AX_LOCAL_PROVIDER` и `AX_LOCAL_MODEL` при запуске. Провайдер берётся из
`config/agents.json`: поддерживаются профили с OpenAI-совместимым HTTP API,
например `openrouter`, `ollama`, `ollama_cloud`, `nous` и `nvidia_nim`.
CLI профили `ollama_claude` и `ollama_claude_local` для AX HTTP harness не подходят.
Все роли из `config/roles.json` сохраняют инструкции и инструменты, но работают
через выбранные провайдер и модель. AX v0.3.1 поддерживает только литералы в
`Task.env`, поэтому ключ провайдера остаётся в API контейнере. В AX Task
передаётся временный токен для ограниченного прокси модели внутри локальной
Docker сети `kind`.

Дополнительные токены сначала разрешаются общим списком имён
`"role_env_names": ["GITHUB_PERSONAL_ACCESS_TOKEN"]` в `config/runtime.json`.
Затем роль выбирает нужные имена через
`"env_names": ["GITHUB_PERSONAL_ACCESS_TOKEN"]` в `config/roles.json`.
Значение `GITHUB_PERSONAL_ACCESS_TOKEN` должно быть задано в окружении AX API; в JSON роли
его не пишут. Служебное окружение AX остаётся доступным, а shell/MCP-инструменты
получают свой обычный минимальный набор переменных плюс явно выбранные и
разрешённые имена.
Отсутствующая или пустая переменная вызывает ошибку запуска этой роли.
AX v0.3.1 сохраняет переданные значения как литералы в спецификации Task;
администраторы с доступом к Task могут их видеть.

`ax_local/config.json` также задаёт AX context и atespace, имя workspace,
ресурсы и режим debug для Task, таймаут маршрута AX, интервалы ожидания запуска, backend сессий,
порт и ограничения прокси модели. Общие настройки ролей и инструментов остаются в `config/roles.json`,
а общие лимиты и таймауты — в `config/runtime.json`. При запуске через Compose
после правки AX конфига повторите команду запуска ниже. При смене AX context
нужен отдельный локальный кластер; для другого atespace заранее нужен
WorkerPool в соответствующем пространстве.

## Делегирование задач между AX-агентами

У ролей с разрешёнными подчинёнными появляется инструмент
`delegate_task(role, task)`. Модель родительского агента вызывает его, API
проверяет разрешение, запускает отдельный AX Task с выбранной ролью, сохраняет
его сессию и возвращает результат родителю. Провайдер и модель дочернего
агента берутся из текущего выбора AX. Нужна модель с поддержкой вызовов инструментов.

Доступные роли задаются полем `allowed_roles` внутри каждой роли в
`config/roles.json`. Например, у `tech_lead`:

```json
"allowed_roles": ["backend_engineer", "frontend_engineer", "qa_engineer", "code_reviewer"]
```

Поле `description` у каждой роли описывает её специализацию и подходящие задачи.
Агент видит эти описания в схеме `delegate_task` только для разрешённых коллег;
предки в цепочке делегирования исключаются, а при исчерпании глубины инструмент
не выдаётся. Для старых конфигураций без `description` используется начало `instructions`.

`backend_engineer` и `frontend_engineer` получили инструкцию перед завершением
изменений передавать их `code_reviewer`. У reviewer подключены навыки ревью,
поиска ошибок, проектирования кода, TDD и передачи контекста, а также GitHub MCP
с инструментами чтения файлов, коммитов и PR, а также публикации замечаний
на строках diff в PR. Reviewer не видит workspace автора:
в `task` нужно передать diff, исходники, требования и результаты проверок либо
доступный repository/ref/PR. Большие изменения передавайте частями с явным
указанием области проверки. Делегирование выбирает модель; это инструкция,
а не обязательный серверный барьер публикации.

Чтобы замечания появились в GitHub, передавайте reviewer URL PR или
`owner`, `repo`, `pullNumber`. Он читает diff и существующие комментарии,
создаёт pending review для проверенного head SHA, добавляет замечания с
`path`, `line`, `side` и публикует review с `event=COMMENT`. В результате
должны быть ссылки на опубликованные замечания. При смене head SHA или чужом
pending review публикация останавливается. Без PR замечания возвращаются
родительскому агенту. При отсутствии замечаний пустые комментарии не создаются.
Токену нужны права **Pull requests: write**; комментарии будут от имени владельца
токена. Инструкция reviewer запрещает approve, merge и изменения исходников.

GitHub MCP авторизуется автоматически через `GITHUB_PERSONAL_ACCESS_TOKEN` из `.env`.
Для чтения репозиториев нужны права чтения, для изменений через `backend_engineer` —
права записи в целевой репозиторий. После обновления выполните `bash ax_local/up.sh`
и создайте новую сессию с `sessionId: ""`.

Роль без `allowed_roles` или с пустым списком не получает инструмент делегирования.
Неизвестные роли, дубли и собственная роль в списке вызывают ошибку конфигурации.
Например, для цепочки
`chat → tech_lead → backend_engineer → qa_engineer` добавьте `tech_lead`
в `chat.allowed_roles`. Проверка разрешений выполняется API по текущему
`config/roles.json` и токену конкретного родительского воркера, независимо
от аргументов модели или конфигурации ранее сохранённой сессии.

Параметры запуска и ограничения `delegation` остаются в `ax_local/config.json`:

| Поле | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `enabled` | `true` | Включает A2A-адаптер и инструмент. |
| `port` | `8005` | Внутренний A2A-порт API на сети kind, без публикации на хост. |
| `max_depth` | `3` | Максимум переходов от родителя к дочерним ролям. Повтор роли в цепочке запрещён. |
| `max_calls_per_turn` | `8` | Общий предел новых дочерних задач во всём дереве за один ход корневого агента. |
| `max_concurrent_tasks` | `4` | Отдельный лимит одновременно выполняемых дочерних задач. При заполнении возвращается ошибка без ожидания свободного слота. |
| `turn_timeout_seconds` | `300` | Бюджет хода агента, которому разрешено делегировать. Запуск и работа потомков входят в оставшийся бюджет родителя. |
| `poll_interval_seconds` | `0.5` | Интервал проверки состояния дочерней задачи. |

После изменения настроек или кода выполните из корня репозитория:

```bash
bash ax_local/up.sh
```

## Задачи по расписанию

В `config/roles.json` у роли можно задать один или несколько запусков через
`cron`. Например:

```json
"cron_demo": {
  "agent": "openrouter",
  "instructions": "You are a demo scheduled agent. Use utc_time to read the current UTC date and time, then report it briefly. Do not guess the time.",
  "tools": ["utc_time"],
  "cron": [{"schedule": "0 9 * * *", "task": "Use utc_time and report the current UTC date and time."}]
}
```

Эта роль уже есть в `config/roles.json` и выполняется ежедневно в 09:00 UTC
после перезапуска AX API с обновлённым конфигом.

AX API выполняет числовые пяти полевые cron-выражения по **UTC** (минута, час,
день месяца, месяц, день недели; воскресенье — `0` или `7`). Поддерживаются
`*`, списки, диапазоны и шаги. Каждый запуск создаёт отдельную сессию роли;
её задача, ответ, время запуска и состояние сохраняются в общей базе сессий.
После выполнения AX Task удаляется. Запуски, пропущенные пока API был выключен,
не восполняются. Повторный старт API в ту же минуту не повторяет уже сохранённый
запуск. Если предыдущий запуск того же расписания ещё работает или заполнен
лимит одновременно выполняемых cron задач (`delegation.max_concurrent_tasks`),
текущая минута пропускается. Изменения `config/roles.json` применяются после
перезапуска AX API. Cron расписания исполняет только AX API; обычный Docker
orchestrator принимает поле при загрузке ролей, но не запускает его.
Пока делегированная или cron задача активна, `DELETE /chats/ID` возвращает
HTTP 409. После завершения задачи сессию можно удалить обычным запросом.

Команда также обновляет локальный AX-контроллер, если адаптация для инструментов
ещё не установлена. В AX v0.3.1 Task не задаёт `securityContext`: процессы
начинают работу с UID 0 без возможности переключить пользователя. Для нашего
образа и ролей с shell, файловыми или MCP-инструментами адаптация добавляет
только `SETUID/SETGID`, чтобы существующий launcher запускал инструменты с
UID/GID 10001. Проверяются закреплённая версия AX и отдельный kubeconfig
`ax_local/.local/kubeconfig`. Повторный запуск не пересобирает контроллер,
если версия адаптации уже установлена.

Entrypoint подготавливает приватную файловую систему actor для UID 10001:
добавляет право прохода через `/` (корень overlay с `0700` становится `0711`)
и устанавливает sticky-права `1777` на `/workspace`. Права записи в `/`
сохраняются; это позволяет инструментам запускать Python и читать его библиотеки.

Для проверки через подключённый к Codex/Claude `popot-ax` MCP попросите:

> Вызови run_task с role="chat" и task="Обязательно используй delegate_task,
> чтобы передать роли analyst вычисление 17 * 19. Получи её ответ и сообщи
> результат и sessionId дочерней сессии."

Или выполните:

```bash
curl --fail-with-body --max-time 660 -sS http://127.0.0.1:8003/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2025-11-25' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"run_task","arguments":{"role":"chat","task":"Обязательно используй delegate_task: передай роли analyst вычисление 17 * 19, получи её ответ и сообщи результат и sessionId дочерней сессии."}}}'
```

Ожидается ответ `323` после фактического вызова `delegate_task`. Дочерняя
сессия видна через MCP `list_chats` и `get_chat`; её связь с родителем,
состояние задачи и результат сохраняются в PostgreSQL вместе с конфигурацией
роли. Состояния переходов также пишутся в логи API как `ax_delegation`.

При ошибке `delegate_task` возвращает `sessionId` и роль упавшего дочернего
агента, безопасную причину в `error` и диагностику `failure`: этап `stage`
(`worker_startup` — запуск AX, `worker_message` — выполнение запроса), код
`code` и тип исключения `error_type`. Эти поля сохраняются в сессии и логах
API. Например, `mcp_discovery_failed` означает сбой подключения MCP-инструментов
дочерней роли до вызова модели. Полный текст исключения в A2A-ответ не попадает.

```bash
docker compose --env-file .env -f ax_local/compose.yaml logs --tail=500 api | grep '"event": "ax_delegation"'
```

Каждое делегирование создаёт новую сессию. Дочерний воркер завершается после
ответа или ошибки; при завершении хода родителя незавершённые потомки
отменяются. Повтор A2A-запроса с тем же `messageId` возвращает существующую
задачу. После перезапуска API прерванные задачи помечаются ошибкой и их
воркеры удаляются; повторный запуск работы требует новой задачи.

Контекст передаётся явно в `task`: требования, текст, JSON или патч.
История родителя и файлы его workspace автоматически не копируются.
У `frontend_engineer` и `qa_engineer` по текущему `config/roles.json` нет
файловых и shell-инструментов: их ответы содержат предложения и сценарии,
а выполнение проверок требует отдельно настроенных инструментов роли.

Локальный адаптер реализует ограниченный набор
[A2A 1.0 JSON-RPC](https://a2a-protocol.org/latest/specification/):
`SendMessage` с неблокирующей отправкой текстовой задачи, `GetTask`,
`CancelTask`, Agent Card по `/a2a/ROLE/.well-known/agent-card.json` и текстовый
результат как Artifact. Клиент использует заголовок `A2A-Version: 1.0`.
Streaming, push notifications, загрузка файлов и полный набор операций A2A
не реализованы. Токен делегирования действует только во время хода его
агента; он не сохраняется в PostgreSQL и не передаётся shell/MCP-процессам.

## Подготовка

Нужны работающий Docker Desktop, `git`, Go 1.27.1+, `kubectl` и Python 3.10+.
Для выбранного провайдера подготовьте его ключ в `.env`, если он требуется.
При отсутствии `ko` bootstrap установит
v0.19.1 в `ax_local/.local/bin`; `kind` ставит скрипт Agent Substrate.
Первый запуск скачивает исходники и контейнерные образы и может занять время.

Из корня репозитория:

```bash
bash ax_local/up.sh
```

При первом запуске команда подготавливает локальный кластер, собирает worker и
поднимает PostgreSQL, API и MCP через Compose. При повторном запуске она
пересобирает worker, обновляет его в локальном registry и пересоздаёт API/MCP.
Используется `POPOT_DB_PASSWORD` из существующего `.env`. Все команды выполняются
через эту точку входа. Она также запускает остановленные локальные контейнеры
`kind-registry` и `popot-ax-control-plane` и выставляет таймаут
`atenet-router` из `ax.route_timeout_seconds` (по умолчанию 330 секунд).
Для настройки роутера скрипт вызывает `kubectl` с явными путём к локальному
`ax_local/.local/kubeconfig` и контекстом `kind-popot-ax`; рабочий контекст
пользователя не меняется.

Для другого провайдера укажите обе переменные и его ключ в `.env`, если нужен.
Например, `nous` использует `NOUS_API_KEY`, а `nvidia_nim` — `NVIDIA_API_KEY`:

```bash
AX_LOCAL_PROVIDER=nous AX_LOCAL_MODEL=ИМЯ_МОДЕЛИ \
  bash ax_local/up.sh
```

Для провайдера по умолчанию можно задать только `AX_LOCAL_MODEL`.
`OLLAMA_MODEL` здесь не используется. Python пакет на хосте устанавливать не
нужно. Команда запуска сама готовит kubeconfig для API контейнера при первом
старте.

Ранее запущенный на хосте `python3 -m ax_local.server` можно остановить через
`Ctrl+C`: Compose запускает собственный API контейнер.

Bootstrap фиксирует AX на `v0.3.1`, Substrate — на commit из его `go.mod`,
строит runner под архитектуру машины и сохраняет digest образа в
`ax_local/.local/worker-image`. Он использует свой `KUBECONFIG` и готовит
копию для API контейнера. API контейнер подключается к Docker сети `kind` и
к Kubernetes API узла `popot-ax-control-plane`, без Docker socket. Если имя `popot-ax` или
`kind-registry` занято несовместимым локальным ресурсом, скрипт останавливается.
Состояние `.local/` игнорируется Git.

Прокси в API контейнере использует endpoint из профиля и принимает запросы
только с токеном текущего запуска. Для локального Ollama проверьте, что он
слушает адрес, доступный Docker контейнерам через `host.docker.internal`.

## Проверка и сравнение

Проверьте контейнеры и вызов существующего MCP инструмента:

```bash
docker compose --env-file .env -f ax_local/compose.yaml ps db api mcp-server
curl --fail-with-body -sS http://127.0.0.1:8003/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2025-11-25' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"run_task","arguments":{"role":"local_analyst","task":"Сколько будет 17 * 19?"}}}'
```

Логи API и MCP при проверке:

```bash
docker compose --env-file .env -f ax_local/compose.yaml logs -f api mcp-server
```

Таймаут одного запроса к модели задаётся в
`config/runtime.json → timeouts.model_request_seconds` (45 секунд по умолчанию).
AX-прокси вычитает `proxy.response_margin_seconds` из `ax_local/config.json`
(5 секунд, но не больше половины лимита), чтобы успеть вернуть HTTP 504 раньше,
чем worker закроет соединение. Это socket timeout, а не гарантия общего времени
всего ответа. Если остаток времени хода меньше, worker может завершиться раньше.
При таймауте провайдера в логах API появляется `model_upstream_timeout` с моделью,
лимитом и временем ожидания; при таймауте в harness — `model_timeout` с номером
раунда. Закрытое клиентом соединение обрабатывается без traceback BrokenPipe.
`config/runtime.json → model.request_retries` задаёт число повторов запроса
к модели при socket timeout или HTTP 502/503/504: целое неотрицательное число,
0 отключает повторы. При отсутствии поля используется 1. Значение 10 разрешает
до десяти повторов после первой попытки, если хватает общего времени хода.
Повторяется только текущая генерация с той же историей и результатами инструментов,
в пределах оставшегося времени хода. Выполненные вызовы инструментов не запускаются
повторно этим механизмом; таймаут самого инструмента завершает ход.
В логах видны `attempt` и `model_retry`. Повтор генерации может дополнительно
тарифицироваться провайдером. HTTP 401/403 повторно не запрашиваются.
После изменения конфигурации/кода примените `bash ax_local/up.sh`.

Первый `run_task` ждёт готовности AX Task до `ax.startup_timeout_seconds` из
`ax_local/config.json`; `curl` до ответа ничего не выводит. Если ожидание
затянулось, проверяйте фазу Task в другом терминале, пока запрос выполняется:

```bash
docker compose --env-file .env -f ax_local/compose.yaml exec -T api \
  ax --context=kind-popot-ax --atespace=ate-demo-counter get tasks
docker compose --env-file .env -f ax_local/compose.yaml logs --since=10m api \
  | rg 'AX task|POST /tasks'
```

После ошибки API удаляет AX Task, поэтому поздний `get tasks` может вернуть
пустой список. В сообщении об ошибке и логах API остаются последняя фаза и
причина из статуса AX; исходные значения окружения Task не выводятся.

Подключение клиентов:

```bash
codex mcp add popot-ax --url http://127.0.0.1:8003/mcp
claude mcp add --transport http popot-ax http://127.0.0.1:8003/mcp
```

Для сравнения запустите текущий Docker вариант через
`docker compose up --build -d mcp-server` и подключите его MCP endpoint на
`http://127.0.0.1:8001/mcp`. Используйте одинаковую роль, провайдера и модель.
MCP инструменты `run_task`, `send_message`, `list_chats` и
`get_chat` одинаковы для обоих вариантов. Сохраните `sessionId` из ответа и
сравните первый ответ, продолжение чата, восстановление после перезапуска,
ошибки модели и работу инструментов. AX использует отдельную базу сессий.
Поле `container` в AX ответе содержит имя AX Task; `workspace` будет `null`,
потому что AX workspace находится внутри actor.
После смены `AX_LOCAL_PROVIDER` создавайте новый чат: сохранённые сессии
предыдущего провайдера доступны при возврате к его конфигурации.

## Восстановление сессии после ошибки очистки workspace

Если API сообщает `Timed out deleting previous AX task`, а контроллер сначала
сообщил `permission denied` при удалении `durable-dir`, затем `runsc state:
exit status 128`, примените локальное исправление для закреплённой версии
Substrate:

```bash
python3 ax_local/cluster/substrate_cleanup.py --apply
```

Без `--apply` команда только выводит описание изменений. При применении она
проверяет отдельный kubeconfig, настроенный kind-контекст и commit Substrate,
добавляет патч в локальный checkout, запускает тест helper, собирает Linux-образ
`atelet` через локальный `ko` и обновляет существующий DaemonSet в `ate-system`.
Сборка или тест с ошибкой останавливают процесс до изменения DaemonSet.

Изменения затрагивают службу очистки `atelet`: ей добавляются файловые
capabilities `DAC_OVERRIDE` и `FOWNER` для удаления каталогов другого UID,
включая вложенные каталоги со sticky bit. Это расширяет доступ `atelet` к
смонтированным файлам; capabilities worker/агентов не меняются. Патч повторной
очистки действует только для gVisor: если bundle и runsc-state существуют и
уже пусты после предыдущего `resetActorDirs`, повторный TerminateWorkload
пропускается и очистка durable-dir продолжается. Ошибки чтения каталогов
останавливают очистку, а не считаются успешным завершением.

После успешного rollout повторите исходный запрос **с тем же `sessionId`**.
API повторно запросит удаление старой Task, создаст worker и восстановит
сохранённую историю из PostgreSQL. Содержимое удаляемого workspace не
восстанавливается из истории. Скрипт не меняет записи сессий и не запускает
повторно пользовательскую задачу самостоятельно.

Это отдельный локальный патч, не обновление upstream Substrate. `ax_local/up.sh`
применяет его автоматически после bootstrap или запуска существующего
kind-кластера, до запуска API. При ошибке установки исправления запуск
останавливается. Повторный upstream deploy `atelet` может заменить образ
или capabilities; следующий `up.sh` обнаружит это и применит исправление снова.

После успешного rollout скрипт сохраняет версию патча и digest образа в
`.local/substrate-cleanup.json`. При следующем запуске он сверяет эти данные
с текущим DaemonSet, проверяет capabilities и ждёт готовности rollout.
Если исправление уже установлено, сборка и обновление DaemonSet пропускаются.
После установки старой версией скрипта без этого файла первый запуск выполнит
сборку ещё раз и создаст отметку для последующих проверок.

## Ограничения опыта

- Адаптер вызывает `ax ssh` для каждого сообщения. Для длинной истории он
  передаёт запрос несколькими частями, так как AX v0.3.1 не пересылает stdin
  в `ax ssh`. Это проверяет AX Task lifecycle, но добавляет накладные расходы
  CLI и туннеля к задержке ответа.
- При idle timeout и удалении чата API удаляет AX Task и восстанавливает
  историю из PostgreSQL при следующем запросе, как Docker вариант. Файлы AX
  workspace после удаления Task не обещают сохраниться; отдельно сравнивайте
  сценарий с файлами до удаления задачи.
- Если удаление старой Task не завершилось, восстановление сессии ждёт его
  в пределах `ax.cli_timeout_seconds` (для делегирования также действует
  оставшийся бюджет родителя). Таймаут этого этапа возвращается как HTTP 502
  с `Timed out deleting previous AX task`, до запуска worker и обращения к
  модели. Неудачная очистка после idle timeout пишет
  `AX task cleanup not confirmed` в лог API. Проверяйте статус Task и лог
  `deployment/ax-controller` в `ax-system`: увеличение лимитов модели
  не устраняет ошибку удаления actor в Substrate.
- В используемой версии Substrate `atelet` работает как UID/GID 0 с
  `capabilities.drop: [ALL]`, а инструменты Popot создают файлы как UID/GID
  10001. Созданные `write_file` каталоги имеют режим `0770` до применения
  umask; очистка durable workspace через `os.RemoveAll` может получить
  `permission denied`. Actor к этому моменту уже остановлен. При повторном
  удалении очистка может упасть раньше на `runsc state` для отсутствующего
  sandbox. Для этого случая выше описан локальный патч `substrate_cleanup.py`;
  одна диагностика адаптера его не исправляет. Не удаляйте записи Task из хранилища вручную: это скроет
  незавершённую очистку ресурсов.
- Используется demo WorkerPool Agent Substrate `ate-demo-counter`, чтобы AX
  Task получил локальную ёмкость. Кластер служит только для разработки.
- Этот вариант не переносит существующие сессии из Docker базы и не меняет
  текущий `compose.yaml`.
