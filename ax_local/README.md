# Локальный вариант на AX

AX — единственный runtime агентов в проекте. Общий HTTP harness, роли, MCP и
хранилище сессий остаются в `popot_agents`; создание и восстановление sandbox
выполняет AX. AX v0.3.1 и совместимый Agent Substrate работают в локальном
кластере `kind-popot-ax` поверх Docker. Compose проект `popot-ax-local` запускает
PostgreSQL, AX API и MCP сервер. MCP доступен на `http://127.0.0.1:8003/mcp`;
API на порту 8002 доступен только контейнерам Compose.

Отдельный Docker runner, его Compose и образы удалены. База и workspace старого
запуска автоматически не переносятся и не удаляются.

Интерактивная [схема архитектуры AX](architecture.html) открывается прямо в
браузере без сервера. Она показывает создание sandbox и harness, suspend/resume,
сохранение среды при ошибке, удаление Task после простоя, A2A-делегирование,
очередь сессий и память проекта Cognee: recall, проверку доказательств,
разделение текста и метаданных, индексацию графа. Это учебная симуляция по коду
проекта, а не live-панель.

## Suspend и продолжение сессии

Режим задаётся полем `snapshot_mode` в `ax_local/config.json`:

- `data` (по умолчанию): Substrate сохраняет durable-файлы `/workspace` в RustFS
  (`ate-snapshots/popot-ax/`). При resume используется штатный `COLD_BOOT`: Python
  запускается из образа с восстановленными файлами, API загружает сохранённый
  диалог перед новым сообщением. Память процесса и фоновые процессы не сохраняются.
- `full`: сохраняет также память процесса. Это явный opt-in для runtime, на котором
  пройден native lifecycle-тест. На текущем локальном ARM64 воспроизведён
  `illegal instruction` после FULL и golden restore; поэтому DATA не использует
  стандартный для AX `GOLDEN` resume.

DATA уменьшает объём сохраняемого состояния, исключая RAM процесса. Чтобы
не раздувать snapshot, держите в `/workspace` рабочие файлы, а временные данные
инструментов — в `/tmp`. Установленные зависимости лучше включать в worker image.
Фрагменты передачи истории находятся в `/tmp` и не попадают в durable snapshot.
`up.sh` применяет настройки контроллера и пересобирает API/worker автоматически.
Уже созданный Task сохраняет свой режим; новая настройка действует на новые Task.

После успешного ответа API сначала сохраняет переписку в PostgreSQL, затем
вызывает `ax suspend task` и ждёт подтверждённого состояния `Suspended`.
`GET /chats` и `GET /chats/{sessionId}` показывают `status: suspended` и не
пробуждают worker. Следующее сообщение через HTTP или MCP с тем же `sessionId`
автоматически вызывает `resume`, ждёт готовности worker, выполняет следующий
ход и снова приостанавливает задачу.

AX Task хранится **7200 секунд (2 часа)** после последнего завершённого хода.
Настройка находится в `suspend_retention_seconds` в `ax_local/config.json` и имеет
приоритет над `ttl_seconds` роли. После этого API удаляет Task, сохраняя историю
сессии. История новых AX-сессий не истекает автоматически; явное удаление чата
удаляет её. Продолжение с тем же ID после таймаута создаёт новый worker с
сохранёнными инструкциями и перепиской. Успешный DATA resume сохраняет файлы
и восстанавливает диалог; после удаления Task восстанавливается переписка,
а не прежняя файловая система.

Если suspend не подтверждён в пределах `cli_timeout_seconds`, API возвращает
уже сохранённый ответ и оставляет Task со статусом `snapshot_unconfirmed`.
Следующий запрос сначала проверяет resume. При ошибке resume API возвращает
HTTP 503, статус становится `resume_failed`: Task, checkpoint и слот сохраняются
для повторной попытки с тем же `sessionId`. Модель не вызывается, среда автоматически
не заменяется пустой. Обычный срок хранения Task продолжает действовать.
События `snapshot_saved` и `snapshot_restored` содержат режим и длительность
операции в секундах; их видно в `activity`, а с непустым `progressToken` — в потоке MCP.
При штатном выключении API его Task удаляются,
а сохранённую переписку можно продолжить после запуска. Дочерние A2A-задачи и
cron сохраняют свой прежний порядок завершения и очистки.

Проверка на локальном AX/Substrate без вызовов модели:

```bash
AX_TEST_LIVE=1 PYTHONDONTWRITEBYTECODE=1 python3 -m unittest ax_local.tests.test_session_lifecycle_live
```

Тест требует три настоящих цикла suspend/resume одного Task с сохранением
файлов и всего диалога, проверяет SHA-256 бинарного файла 1 MiB и историю
после удаления Task. Подмена resume новой пустой средой приводит к падению теста.
Для проверки FULL используйте `AX_TEST_SNAPSHOT_MODE=full`; для другого образа —
`AX_TEST_WORKER_IMAGE=localhost:5001/popot-agent-ax@sha256:...`.
Двухчасовой таймаут проверяется с искусственно увеличенным возрастом сессии.

## Лимит worker и очередь запуска

Один процесс AX API допускает не более **10 созданных worker**: учитываются
запуск, running и suspend. При заполненном лимите новый запуск ждёт в очереди
FIFO до **3600 секунд (1 часа)**. Слот резервируется до создания AX Task;
ожидающие запросы не создают дополнительные sandbox. Когда worker удалён,
первый ожидающий запрос получает освободившийся слот. Через час ожидания без
слота API возвращает HTTP 503 с сообщением `AX worker queue timed out`;
новый worker и вызов модели при этом не запускаются.

Параметры `max_workers` и `worker_queue_timeout_seconds` находятся в
`ax_local/config.json`. Worker в suspend занимает слот до удаления по двухчасовому
таймауту или явного удаления чата. Продолжение существующего worker не занимает
дополнительный слот. Пересоздание после истечения срока
снова проходит через очередь, сохраняя историю сессии.

Этот лимит относится к Popot-сессиям. Штатный планировщик Substrate размещает
акторы на вычислительных worker из `WorkerPool`; suspend освобождает такую
вычислительную мощность. Его request parking ожидает свободную мощность для
resume, поэтому не реализует правило «suspended-сессия занимает слот до удаления».
API добавляет только учёт сессий и очередь допуска к запуску, используя AX
для самого запуска и жизненного цикла.

В Lens вычислительные pod имеют имена `popot-workers-<hash>-<suffix>`:
`worker_pool_name` в `ax_local/config.json` задаёт имя WorkerPool. Пространство
`ate-demo-counter` сохраняется для совместимости с существующими AX-сессиями.
Пул содержит три вычислительных worker; лимит десяти выше относится к сессиям.
Одна сессия — AX Task/actor внутри worker, а не отдельный Kubernetes pod.

`bootstrap.sh`, `up.sh` и `rebuild-worker.sh` переводят прежний пул `counter`
в `popot-workers`: копируют образ, replicas, sandbox class и настройки template,
ждут готовности новых pod и регистрации в Substrate, затем удаляют старый пул.
Миграция ждёт освобождения старых worker акторами из всех atespace, включая
внутренние golden actors; при таймауте занятый пул сохраняется, запуск прекращается.
Идентификаторы сессий и snapshots при переименовании сохраняются. Выполняйте
передеплой между запросами: запуск также может заменять неисправные worker.

После успешного запуска API/MCP `up.sh` автоматически запускает
`cluster/deployment_cleanup.py`. Очистка ограничена локальным kind-контекстом,
`ate-system`, `ax-system` и выбранным atespace. Она удаляет завершённые/ошибочные
Job, терминальные pod и старые ReplicaSet с нулевыми replicas. Текущая версия
Deployment и одна предыдущая версия остаются для rollback. Работающие ресурсы,
AX Task, переписка, snapshots и тома базы сохраняются.

В Docker удаляются остановленные Compose-контейнеры Popot только из этого
checkout и неиспользуемые dangling-образы с меткой `com.popot.project=popot-agents`.
Эту метку получают новые образы AX API, worker, MCP и Cognee UI. Образы без метки, локальный
registry, общие зависимости и build cache не очищаются. Повторный запуск не
перезапускает здоровые Kubernetes pod ради очистки. Ошибка очистки возвращает
ненулевой код `up.sh`; повторить её отдельно можно командой:

```bash
python3 ax_local/cluster/deployment_cleanup.py
```

HTTP, cron и A2A используют общий лимит runner. Для A2A действует также
оставшийся срок родительской задачи, поэтому дочерний запуск может ждать
меньше часа. Отдельного лимита на параллельные дочерние/cron-задачи нет:
их запуск также проходит через общую очередь на 10 worker.
Ожидающие запуски не занимают прежний HTTP семафор на три запроса; работающая
сессия и удаление чата доступны при заполненной очереди.

Слот освобождается только после подтверждённого удаления AX Task. При сбое
очистки API сохраняет резерв и повторяет удаление во время обслуживания.
При штатном выключении API ожидание в очереди прерывается. Очередь хранится
в памяти процесса: после перезапуска нужно повторить незапущенный запрос.
При старте API удаляет оставшиеся Popot Task предыдущего процесса, поскольку
его proxy-токен уже недействителен; сохранённая история остаётся доступной.
Лимит действует для одного API процесса, не является распределённой квотой
для нескольких независимых API и не меняет размер `WorkerPool`.

MCP использует общий `timeouts.mcp_upstream_seconds = 7200` из
`config/runtime.json`, чтобы покрыть час очереди, подготовку worker и новый ход.
HTTP/MCP-клиент должен также допускать такое длительное ожидание.

Версии MCP-пакетов для gateway и AX worker: они закреплены в корневом
`pyproject.toml`, в группах `mcp` и `worker`. Сервер, клиент worker, адаптер
Cognee и совместимые Fetch/Git используют SDK 2.x. После изменения версий `bash ax_local/up.sh`
пересобирает образы. Сервер поддерживает протокол `2026-07-28` и совместимые
запросы `2025-11-25` из примеров ниже; клиент worker согласует версию автоматически.

Параметры модели берутся из `model_parameters` выбранного провайдера в
`config/agents.json` и передаются через `HARNESS_MODEL_PARAMETERS_JSON` всем
его worker, включая дочерние A2A-задачи. В профилях `openrouter` и `nous` явно
задано `"model_parameters": {"reasoning": {"enabled": true, "exclude": false}}`.
Каталоги провайдеров подтверждают поддержку для `openrouter/free` и
`inclusionai/ling-3.0-flash-fin:free` (проверено 2026-10-10). OpenRouter вернул
reasoning в проверочном запросе; старая модель Nous возвращала HTTP 404 и с
параметром, и без него. На 2026-10-18 `NOUS_MODEL` заменён локально на
`upstage/solar-mini4:free`, которая прошла два хода с инструментами через OmniRoute.
Настройка применяется к ролям с `agent: "openrouter"` или `agent: "nous"`
соответственно. Дочерняя задача выбирает профиль своей роли. Для выбора глубины
можно заменить `enabled` на `"effort": "medium"`
и пересобрать стек через `bash ax_local/up.sh`. Вместо `effort` можно указать
`reasoning.max_tokens`, а `{"enabled": true}` использует настройки провайдера
по умолчанию. Поддержка зависит от модели; `openrouter/free` выбирает её
динамически. Профиль `nvidia_nim` настроен на
`NVIDIA_MODEL=nvidia/nemotron-3-super-120b-a12b` в `.env` и `.env.example`;
thinking явно включён его нативным параметром
`"model_parameters": {"chat_template_kwargs": {"enable_thinking": true}}`.
Проверочный вызов NVIDIA прошёл цикл «инструмент → результат → ответ» и вернул
reasoning. Чтобы выбрать этот профиль, задайте `"agent": "nvidia_nim"` нужной
роли в `config/roles.json`, настройте `NVIDIA_MODEL` и `NVIDIA_API_KEY` в `.env`,
затем выполните `bash ax_local/up.sh`.
У локального `qwen2.5-coder:14b` thinking-режим не заявлен; профили Ollama
сейчас не назначены ролям.
Это настройка профиля; в аргументы MCP `run_task` её добавлять не нужно.

`run_task` и `send_message` передают исходные события HTTP harness через
стандартные MCP `notifications/progress`. Поле `message` содержит JSON события
с его исходным `event` и полями: `assistant_message`/`assistant_answer` с текстом,
`tool_call`, `tool_result`, `tool_error`, события модели, памяти и сессии.
Событие `assistant_reasoning` передаёт возвращённые провайдером поля `reasoning`,
`reasoning_content` и `reasoning_details`, если они есть. Harness получает ответ
модели целиком: это событие приходит после каждого ответа модели, до её
инструментов или итогового ответа пользователю, а не по отдельным токенам.
При `reasoning.exclude: true` провайдер может не вернуть текст reasoning;
harness ничего не добавляет от себя и не расшифровывает непрозрачные блоки.
Словаря переводов и списка разрешённых имён событий нет. Диагностические строки
harness приходят как `output` с полями `stream` и `content`. Ключи, токены и
другие распознаваемые секреты маскируются и в потоке, и в журнале harness.
Передаются поля, которые сам harness пишет в журнал: например, некоторые
инструменты выдают в trace `output_chars`, а не полное содержимое файла.

Клиент должен передать непустой `params._meta.progressToken` в `tools/call` и показывать
progress notifications. Если токен отсутствует, равен `null` или `""`, уведомления
прогресса отключены для `run_task` и `send_message`. Числовой `0` остаётся допустимым
токеном. Итоговый ответ и `activity` возвращаются и без уведомлений; служебные SSE
`ping` могут оставаться. В Python MCP SDK токен передаёт `progress_callback` у
`Client.call_tool`; для curl используйте `-N`. Числовой progress считает
события, а не процент готовности; total не задаётся. Поток не останавливается
после 200 событий и не скрывает одинаковые последовательные события.
Итоговый `activity` содержит последние 20 событий, а `answer` и `sessionId`
сохраняются. MCP использует Streamable HTTP: события передаются через SSE,
а протокол `2026-07-28` может вернуть быстрый ответ без событий обычным JSON. Обычный HTTP API
продолжает возвращать JSON; для потоковых событий запросите
`Accept: application/x-ndjson` у `/tasks` или `/messages`.
Обрыв соединения не повторяет и не откатывает действия агента.

События дочерних агентов передаются в тот же поток с дополнительным полем
`agent_role`, которое сохраняется при вложенном делегировании. Родитель
получает их при A2A-опросе задачи (обычно каждые 0,5 секунды); повторные ответы
опроса не дублируют события. Дочерняя задача хранит до 64 последних событий,
но не более 64 КиБ или четверти `limits.history_bytes` (меньшее из значений).
Одно событие занимает не более 16 КиБ сериализованного JSON, включая экранирование;
при меньшем общем бюджете сокращается и этот предел. Большое событие сохраняет
`event` и `agent_role`, получает `truncated: true`, `original_bytes` и исходный
фрагмент в `preview`. Старые события могут выпасть из окна. При формировании
A2A-ответа прогресс дополнительно сокращается, чтобы оставить место результату
задачи и служебным полям протокола; текст результата этим механизмом не обрезается.
Служебные `ping` остаются между событиями, например во время ожидания ответа модели.

Проверка прогресса в реальном sandbox без вызова модели: скопируйте
`ax_local/tests/test_progress_live.py` в `/tmp/test_progress_live.py` контейнера API
и выполните `docker exec -e AX_TEST_PROGRESS_LIVE=1 popot-ax-local-api-1 python /tmp/test_progress_live.py`.

Проверка 10 suspended-сессий и запуска одиннадцатой после освобождения слота
без вызова модели:

```bash
AX_TEST_LIVE_QUEUE=1 PYTHONDONTWRITEBYTECODE=1 python3 -m unittest ax_local.tests.test_worker_queue_live
```

## Где что находится

`up.sh` also starts the shared Cognee memory and graph UI at
**http://localhost:3001**. Sign in as `default_user@example.com` with
`COGNEE_PASSWORD` from the root `.env`. Agent memory is visible under **Brains**
after indexing. Details: [memory/README.md](../memory/README.md).

Поле `skills` в `config/roles.json` задаёт навыки роли, например
`["engineering/codebase-design", "engineering/tdd"]`. API проверяет пути,
а AX worker загружает выбранные Markdown-файлы в инструкции harness до
начала обслуживания сессии. Подробности и каталог: [skills/README.md](../skills/README.md).
После изменения навыков выполните `bash ax_local/rebuild-worker.sh` из корня
репозитория и начните новую сессию. В логах воркера появится `skills_loaded`.

| Путь | Назначение |
| --- | --- |
| `../config/runtime.json` | Общие настройки harness, сессий, памяти, таймаутов и лимитов. |
| `config.json` | Настройки AX: кластер, ресурсы, очередь, A2A и proxy. |
| `config.py` | Загрузка и проверка AX-конфига с учётом общих таймаутов. |
| `../popot_agents/runtime_config.py` | Загрузка и проверка общих настроек. |
| `api/server.py` | HTTP API, роли и хранение сессий. |
| `api/ax_runner.py` | Создание AX Task и обмен сообщениями через `ax ssh`. |
| `api/provider_proxy.py` | Доступ Task к выбранному провайдеру без передачи его ключа в Task. |
| `api/delegation.py` | A2A-задачи, проверка разрешённых ролей, запуск и завершение дочерних агентов. |
| `api/cron.py` | Запуск задач ролей по cron в AX API. |
| `worker/delegation.py` | Инструмент `delegate_task` внутри AX harness. |
| `worker/` | Код, выполняемый внутри AX Task. |
| `cluster/` | Подготовка kubeconfig для API контейнера. |
| `cluster/controller_tools.*` | Локальная адаптация AX-контроллера для запуска инструментов с UID/GID 10001. |
| `docker/` | Dockerfile и списки файлов для сборки API и Task образов. |
| `tests/` | Локальные тесты AX варианта. |

`up.sh` — единая команда для первого и повторного запуска. Файлы `server.py` и
`container_kubeconfig.py` в корне папки сохраняют прежние команды как короткие
переходники к новым модулям.

Перед запуском API/MCP `up.sh` проверяет pod и реестр worker Substrate.
После перезапуска Docker/kind IP pod может измениться, а в реестре остаться
старым. Скрипт пересоздаёт только Ready pod с подтверждённым расхождением IP
и тем же UID, затем ждёт регистрации всех реплик WorkerPool с актуальными IP.
Исправные pod не перезапускаются. Такая же проверка есть в `rebuild-worker.sh`.
CLI проверки собирается один раз из закреплённой версии Substrate в `.local`.

После перезапуска Docker/kind выполняйте из корня репозитория:

```bash
bash ax_local/up.sh
```

Ожидание ограничено `ax.startup_timeout_seconds` (по умолчанию 300 секунд).
Если восстановление не завершилось, скрипт завершается с ошибкой до запуска
Compose API/MCP. Уже запущенные контейнеры Compose при этом не останавливаются.
Пересоздание неисправного worker прерывает задачи на нём; запускайте скрипт
до отправки новых запросов. Это проверка при запуске, а не постоянный монитор:
после следующего перезапуска кластера нужно снова выполнить `up.sh`.

Роль выбирает профиль через `agent` в `config/roles.json`. Профиль из
`config/agents.json` задаёт endpoint, имя переменной модели (`model_env`) и
параметры модели. Значение модели берётся из `.env`: например,
`backend_engineer → omniroute_code → OMNIROUTE_CODE_MODEL`,
`analyst → omniroute → OMNIROUTE_MODEL`,
`chat → openrouter → OPENROUTER_MODEL`. Общего провайдера или модели AX нет.
Дочерние A2A-задачи и cron также используют профиль своей роли. Все профили
делят одну очередь с общим лимитом `max_workers`.

Поддерживаются профили с OpenAI-совместимым HTTP API: `openrouter`, `ollama_local`,
`ollama_cloud`, `nous`, `nvidia_nim`, `omniroute` и `omniroute_code`. CLI-профили `ollama_claude` и
`ollama_claude_local` удалены: AX использует HTTP harness. API при старте проверяет
модели и необходимые ключи только для профилей, используемых ролями; отсутствие
этих настроек приводит к явной ошибке. Неиспользуемым профилям ключи не нужны.

AX v0.3.1 поддерживает только литералы в `Task.env`, поэтому ключ провайдера
остаётся в API-контейнере. В AX Task передаётся временный токен прокси, привязанный
к конкретному профилю и модели. Прокси доступен внутри локальной Docker-сети `kind`.

Дополнительные токены сначала разрешаются общим списком имён
`"role_env_names": ["GITHUB_PERSONAL_ACCESS_TOKEN"]` в `config/runtime.json`.
Затем роль выбирает нужные имена через
`"env_names": ["GITHUB_PERSONAL_ACCESS_TOKEN"]` в `config/roles.json`.
Значение `GITHUB_PERSONAL_ACCESS_TOKEN` должно быть задано в окружении AX API; в JSON роли
его не пишут. Служебное окружение AX остаётся доступным, а shell/MCP-инструменты
получают свой обычный минимальный набор переменных плюс явно выбранные и
разрешённые имена.
Отсутствующая или пустая переменная вызывает ошибку запуска этой роли.
AX v0.3.1 сохраняет переданные значения как литералы в спецификации Task;
администраторы с доступом к Task могут их видеть.

Файл `ax_local/config.json` задаёт context и atespace, workspace,
ресурсы и debug для Task, таймауты AX, backend сессий, `delegation` и `proxy`.
Внешнего раздела `ax` в нём нет. Общие таймауты модели, инструментов и хода,
настройки памяти и ограничения сообщений остаются в `config/runtime.json`.
Все значения задаются явно: старые поля и пропущенные обязательные настройки
отклоняются при загрузке. AX проверяет свои таймауты относительно общих бюджетов.
При прямом запуске Python можно выбрать файлы через `POPOT_AX_CONFIG` и
`POPOT_RUNTIME_CONFIG`; локальные скрипты читают `ax_local/config.json` из репозитория.
Роли и инструменты остаются в `config/roles.json`, провайдеры — в `config/agents.json`.
При запуске через Compose после правки конфига повторите команду запуска ниже. При смене AX context
нужен отдельный локальный кластер; для другого atespace заранее нужен
WorkerPool в соответствующем пространстве.

## OmniRoute для AX

Необязательный профиль `omniroute` использует цепочку
`AX worker → AX API proxy → OmniRoute → провайдер`.
Версия Docker-сервиса задаётся `OMNIROUTE_VERSION` в `pyproject.toml`, панель доступна только
на `http://127.0.0.1:20128`. Настройки, ключи провайдеров и история шлюза хранятся
в volume `omniroute-data`. Это один экземпляр без Redis: rate limiter использует
in-memory fallback, его локальное состояние сбрасывается при перезапуске.
Квоты самих провайдеров от этого не увеличиваются.

Текущие маршруты выбраны по отчёту
`reports/vps-models-20261018T122551Z/recommendations.json` и проверены локально
на двух сообщениях с вызовами `calculate`. Порядок целей в `priority`:

| Комбо | Роли | Порядок моделей |
| --- | --- | --- |
| `ax-free` | `analyst` | NVIDIA Nemotron Super → OpenRouter Nemotron Super `:free` → OpenRouter North Mini Code `:free` → Nous Solar Mini 4 `:free` |
| `ax-code-free` | `backend_engineer`, `frontend_engineer`, `code_reviewer` | OpenRouter North Mini Code `:free` → NVIDIA Nemotron Super → OpenRouter Nemotron Super `:free` → Nous Solar Mini 4 `:free` |

Точные model IDs: `nvidia/nemotron-3-super-120b-a12b` у NVIDIA,
`nvidia/nemotron-3-super-120b-a12b:free` и `cohere/north-mini-code:free` у
OpenRouter, `upstage/solar-mini4:free` у Nous (`nous-research` в OmniRoute).
Solar стоит последним: короткая локальная проверка не заменяет статистику
надёжности. Обязательные reasoning-модели из списка кандидатов пока не включены.
Hosted-доступ NVIDIA здесь используется для локальной разработки в рамках
[Developer Program](https://docs.api.nvidia.com/nim/docs/product), с лимитами
аккаунта; это не обещание бесплатного production-развёртывания.
Переключение модели внутри OpenRouter не создаёт отдельную аккаунтную квоту.

1. В корневом `.env` задайте стойкий `OMNIROUTE_INITIAL_PASSWORD` для первого
   входа в панель. В версии 3.8.51 пустое значение оставляет первичную настройку
   незавершённой; пароль автоматически в логах не появляется.
   Запустите только шлюз из корня репозитория:

   ```bash
   bash compose.sh --env-file .env -f ax_local/compose.yaml up -d --wait --wait-timeout 180 omniroute
   ```

2. Откройте панель. В **Providers** добавьте свои ключи провайдеров, а в
   **Combos** создайте `ax-free` и `ax-code-free` со стратегией `priority`. Добавьте
   конкретные модели, доступные бесплатно вашим аккаунтам, в порядке предпочтения:
   сильную модель первой, затем бесплатные запасные у других провайдеров.
   Для ролей с инструментами все targets должны поддерживать tool calling.
   Локальная Ollama из контейнера доступна по `http://host.docker.internal:11434/v1`.
   В **Endpoints** создайте ключ самого OmniRoute и сохраните его в `.env`:

   ```dotenv
   OMNIROUTE_API_KEY=<gateway-key-from-OmniRoute>
   OMNIROUTE_MODEL=ax-free
   OMNIROUTE_CODE_MODEL=ax-code-free
   ```

   Для этого ключа включите ограниченный доступ к моделям: разрешите только
   бесплатные targets и комбо `ax-free`/`ax-code-free`, привяжите разрешённые подключения.
   Отключите Auto Combos. Сжатие контекста для начальной проверки отключите,
   чтобы шлюз передавал историю инструментов без преобразований.

   AX не проверяет стоимость моделей. В `ax-free` должны быть только явно
   выбранные бесплатные targets: без `auto`, платных моделей и платных
   fallback-targets. Если аккаунт допускает платный перерасход бесплатной квоты,
   запретите его у провайдера. `auto/...:free` не даёт строгой гарантии:
   [фильтрация OmniRoute работает fail-open](https://github.com/diegosouzapw/OmniRoute/blob/v3.8.51/docs/routing/AUTO-COMBO.md).
   При недоступности всех бесплатных targets задача может завершиться ошибкой.

3. В `config/roles.json` роль `analyst` уже выбирает `"agent": "omniroute"`.
   `backend_engineer`, `frontend_engineer` и `code_reviewer` выбирают
   `"agent": "omniroute_code"`. Примените конфигурацию
   через `bash ax_local/up.sh` и начните новую сессию. Проверочный MCP-вызов:

   ```json
   {"name":"run_task","arguments":{"role":"analyst","task":"Используй calculate для 17 * 19 и сообщи результат."}}
   ```

Ключ шлюза и обе модели-комбо обязательны для запуска AX, пока роли выбирают
`omniroute` и `omniroute_code`. Чтобы запустить AX без шлюза, назначьте этим
ролям другой настроенный профиль, например `openrouter`. `up.sh` сам не запускает
необязательный шлюз; запускайте его командой из шага 1. Его ключ остаётся в AX API,
worker получает только токен прокси. Ключи upstream-провайдеров добавляются в
панели OmniRoute отдельно: переменные `OPENROUTER_API_KEY`, `NVIDIA_API_KEY` и
другие из `.env` автоматически в шлюз не импортируются.

В панели **Combos**, **Providers** и **Quota** проверяйте выбранные модели,
ошибки, переключения и использование квот. Python-прокси AX передаёт тело ответа,
но не пробрасывает `X-OmniRoute-*` заголовки; метрики шлюза в Grafana этим
подключением не добавляются.

Офлайн-проверка профиля, tool loop и изоляции ключа:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest ax_local.tests.test_omniroute
```

## Планировщик и спецификации

Роль `planner` обсуждает задачу с пользователем, готовит спецификацию и
координирует выполнение через существующий `delegate_task`. Выберите её в
MCP-вызове `run_task` или первом `POST /messages`:

```json
{
  "role": "planner",
  "message": "Обсудим поиск по каталогу. Подготовь спецификацию и критерии приёмки; реализацию пока не начинай."
}
```

Для следующего этапа продолжайте тот же `sessionId`, например:

```json
{
  "sessionId": "<ID из предыдущего ответа>",
  "message": "Реализуй согласованную SPEC-1: делегируй задачи специалистам и проверь результаты."
}
```

Для роли включены восемь навыков Matt Pocock: `grilling`, `grill-with-docs`,
`domain-modeling`, `to-spec`, `to-tickets`, `code-review`,
`setup-matt-pocock-skills` и `handoff`. Словарь, ADR и справочники локального
трекера уже загружаются в prompt. По умолчанию specs и задачи — локальные
drafts в `/workspace/specs`; подключение setup не запускает настройку или
внешнюю публикацию. Подборка и ограничения: [skills/README.md](../skills/README.md).

Инструкции планировщика задают следующий процесс:

1. Уточнить цель, границы, ограничения и неизвестные детали. В режиме
   обсуждения или подготовки spec не начинать реализацию.
2. Подготовить spec с ID/версией, поведением, контрактами, зависимостями,
   критериями `AC-*`, планом проверки и задачами `T-*` с владельцами.
3. Передать специалистам конкретные задачи со spec, входными данными,
   критериями приёмки, разрешённым объёмом действий и требуемыми доказательствами.
4. Получить ответы отдельных worker, сопоставить их с критериями, запросить
   `code_reviewer` и `qa_engineer` для проверки изменений. Успешное завершение
   дочернего вызова само по себе не означает приёмку результата.
5. Зафиксировать по каждой задаче `accepted`, `needs_changes` или `blocked`:
   решение, основание и следующий шаг. Передать замечания на доработку и
   проверить следующую версию перед итоговым ответом пользователю.

Планировщик может обращаться к product manager, designer, tech lead,
backend/frontend engineer, QA, reviewer, data analyst и analyst. Реализация
передаётся непосредственно инженерам, чтобы оставить глубину для их проверок.
Для planner и потомков действуют общий лимит **10 worker**, очередь до часа,
`max_depth = 3`, **8 новых дочерних задач на дерево за ход** и оставшийся срок
родительского хода. Если бюджета не хватило, planner должен сохранить spec,
решения и незавершённые задачи в ответе для следующего продолжения.

У planner есть файловые инструменты для `/workspace/specs`, без shell и
GitHub-токена. Полный текущий spec и решения остаются также в ответах сессии:
файлы sandbox не являются постоянным общим хранилищем. Дочерние worker
не видят его workspace или историю, поэтому spec передаётся текстом, а
результаты должны содержать diff/артефакт или доступную ссылку с проверками.
Приёмка planner не даёт отдельного разрешения на публикацию, merge или deploy.

Это поведение задаётся инструкциями роли и использует существующий A2A
механизм. Оно требует модели с поддержкой вызовов инструментов; при отсутствии
доступа или проверок planner обязан сообщить, что осталось неподтверждённым.

## Делегирование задач между AX-агентами

У ролей с разрешёнными подчинёнными появляется инструмент
`delegate_task(role, task)`. Модель родительского агента вызывает его, API
проверяет разрешение, запускает отдельный AX Task с выбранной ролью, сохраняет
его сессию и возвращает результат родителю. Провайдер и модель дочернего
агента берутся из текущего выбора AX. Нужна модель с поддержкой вызовов инструментов.

Доступные роли задаются полем `allowed_roles` внутри каждой роли в
`config/roles.json`. Например, у `tech_lead`:

```json
"allowed_roles": ["backend_engineer", "frontend_engineer", "qa_engineer", "code_reviewer"]
```

Поле `description` у каждой роли описывает её специализацию и подходящие задачи.
Агент видит эти описания в схеме `delegate_task` только для разрешённых коллег;
предки в цепочке делегирования исключаются, а при исчерпании глубины инструмент
не выдаётся. Для старых конфигураций без `description` используется начало `instructions`.

Runtime автоматически вызывает нужного коллегу, когда пользователь явно просит
передать задачу одной разрешённой роли. Запрос PR review и продолжение
«оставь комментарии в PR» направляются в `code_reviewer`, если эта роль разрешена.
Родитель получает фактический ответ reviewer вместе с его `sessionId`; для такого
маршрута модель родителя и её файловые/GitHub-инструменты не вызываются.
При отсутствии доступного инструмента делегирования возвращается ошибка.
Запросы с исправлением или реализацией проходят через обычный цикл координации
родителя, включая задачи «передай ревью, затем сам исправь замечания».

В любой вызов `delegate_task` runtime добавляет исходные запросы пользователя,
ограничения на публикацию и предыдущий ответ как неподтверждённый контекст.
Пользовательские ограничения не обрезаются: слишком большой контекст требует
новой сессии с нужными требованиями и доступной ссылкой на исходники.
Ошибка, пустой или обрезанный ответ дочернего агента не допускают успешного
итогового ответа родителя. Перед повтором внешней записи нужно проверить
дочернюю сессию, чтобы не продублировать опубликованные изменения.
Ошибки учитываются отдельно по роли и тексту задания: успешная проверка UI
не закрывает ошибку проверки API, даже если обе выполнял `qa_engineer`.
Успешный повтор той же роли с тем же заданием закрывает только его ошибку.
При исчерпании времени частичный ответ явно перечисляет оставшиеся ошибки.

`backend_engineer` и `frontend_engineer` получили инструкцию перед завершением
изменений передавать их `code_reviewer`. У reviewer подключены навыки ревью,
поиска ошибок, проектирования кода, TDD и передачи контекста, а также GitHub MCP
с инструментами чтения файлов, коммитов и PR, а также публикации замечаний
на строках diff в PR. Reviewer не видит workspace автора:
в `task` нужно передать diff, исходники, требования и результаты проверок либо
доступный repository/ref/PR. Большие изменения передавайте частями с явным
указанием области проверки. Для проверки после реализации делегирование по-прежнему
выбирает модель; обязательный маршрут выше относится к явным запросам специалисту
и отдельным запросам PR review, а не к барьеру публикации любых изменений.

Чтобы замечания появились в GitHub, передавайте reviewer URL PR или
`owner`, `repo`, `pullNumber`. Он читает diff и существующие комментарии,
создаёт pending review для проверенного head SHA, добавляет замечания с
`path`, `line`, `side` и публикует review с `event=COMMENT`. В результате
должны быть ссылки на опубликованные замечания. При смене head SHA или чужом
pending review публикация останавливается. Без PR замечания возвращаются
родительскому агенту. При отсутствии замечаний пустые комментарии не создаются.
Токену нужны права **Pull requests: write**; комментарии будут от имени владельца
токена. Инструкция reviewer запрещает approve, merge и изменения исходников.

GitHub MCP авторизуется автоматически через `GITHUB_PERSONAL_ACCESS_TOKEN` из `.env`.
Для чтения репозиториев нужны права чтения, для изменений через `backend_engineer` —
права записи в целевой репозиторий. После обновления выполните `bash ax_local/up.sh`
и создайте новую сессию с `sessionId: ""`.

Роль без `allowed_roles` или с пустым списком не получает инструмент делегирования.
Неизвестные роли, дубли и собственная роль в списке вызывают ошибку конфигурации.
Например, для цепочки
`chat → tech_lead → backend_engineer → qa_engineer` добавьте `tech_lead`
в `chat.allowed_roles`. Проверка разрешений выполняется API по текущему
`config/roles.json` и токену конкретного родительского воркера, независимо
от аргументов модели или конфигурации ранее сохранённой сессии.

Параметры запуска и ограничения `delegation` находятся в `ax_local/config.json`:

| Поле | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `enabled` | `true` | Включает A2A-адаптер и инструмент. |
| `port` | `8005` | Внутренний A2A-порт API на сети kind, без публикации на хост. |
| `max_depth` | `5` | Максимум переходов от родителя к дочерним ролям. Повтор роли в цепочке запрещён. |
| `max_calls_per_turn` | `8` | Общий предел новых дочерних задач во всём дереве за один ход корневого агента. |
| `turn_timeout_seconds` | `900` | Бюджет хода агента, которому разрешено делегировать. Запуск и работа потомков входят в оставшийся бюджет родителя. |
| `poll_interval_seconds` | `0.5` | Интервал проверки состояния дочерней задачи. |

HTTP, A2A и cron используют общие `max_workers` и
`worker_queue_timeout_seconds`. Отдельного лимита для дочерних задач нет.

После изменения настроек или кода выполните из корня репозитория:

```bash
bash ax_local/up.sh
```

## Задачи по расписанию

В `config/roles.json` у роли можно задать один или несколько запусков через
`cron`. Например:

```json
"cron_demo": {
  "agent": "openrouter",
  "instructions": "You are a demo scheduled agent. Use utc_time to read the current UTC date and time, then report it briefly. Do not guess the time.",
  "tools": ["utc_time"],
  "cron": [{"schedule": "0 9 * * *", "task": "Use utc_time and report the current UTC date and time."}]
}
```

Эта роль уже есть в `config/roles.json` и выполняется ежедневно в 09:00 UTC
после перезапуска AX API с обновлённым конфигом.

AX API выполняет числовые пяти полевые cron-выражения по **UTC** (минута, час,
день месяца, месяц, день недели; воскресенье — `0` или `7`). Поддерживаются
`*`, списки, диапазоны и шаги. Каждый запуск создаёт отдельную сессию роли;
её задача, ответ, время запуска и состояние сохраняются в общей базе сессий.
После выполнения AX Task удаляется. Запуски, пропущенные пока API был выключен,
не восполняются. Повторный старт API в ту же минуту не повторяет уже сохранённый
запуск. Если предыдущий запуск того же расписания ещё работает или ждёт
worker, текущая минута пропускается. При заполненном общем лимите 10 worker
запуски разных расписаний ждут в очереди до часа. Изменения `config/roles.json`
применяются после перезапуска AX API. Cron расписания исполняет AX API.
Пока делегированная или cron задача активна, `DELETE /chats/ID` возвращает
HTTP 409. После завершения задачи сессию можно удалить обычным запросом.

Команда также обновляет локальный AX-контроллер, если адаптация для инструментов
ещё не установлена. В AX v0.3.1 Task не задаёт `securityContext`: процессы
начинают работу с UID 0 без возможности переключить пользователя. Для нашего
образа и ролей с shell, файловыми или MCP-инструментами адаптация добавляет
`CHOWN`, `DAC_OVERRIDE` и `FOWNER` для подготовки и доступа harness к приватному workspace,
а также `SETUID/SETGID`, чтобы launcher запускал инструменты с UID/GID 10001
без Linux capabilities. Проверяются закреплённая версия AX и отдельный kubeconfig
`ax_local/.local/kubeconfig`. Повторный запуск не пересобирает контроллер,
если версия адаптации уже установлена.

Entrypoint подготавливает приватную файловую систему actor для UID 10001:
добавляет право прохода через `/` (корень overlay с `0700` становится `0711`)
и назначает `/workspace` владельца UID/GID 10001 с правами `0700`. Для ролей
без локальных инструментов workspace остаётся у root с теми же закрытыми правами.
При DATA resume права устанавливаются повторно; отказ в смене владельца
останавливает запуск, без перехода к общедоступным правам. Управляющий socket
находится вне пользовательского workspace: `/run/popot/chat.sock`, в каталоге
root с правами `0700`. Инструменты не могут подменить его. Права записи в `/`
сохраняются; это позволяет инструментам запускать Python и читать его библиотеки.
После обновления нужны новая адаптация контроллера (`bash ax_local/cluster/controller_tools.sh`)
и пересборка API/worker (`bash ax_local/up.sh`); существующие Tasks используют старый шаблон.

Для проверки через подключённый к Codex/Claude `popot-ax` MCP попросите:

> Вызови run_task с role="chat" и task="Обязательно используй delegate_task,
> чтобы передать роли analyst вычисление 17 * 19. Получи её ответ и сообщи
> результат и sessionId дочерней сессии."

Или выполните:

```bash
curl --fail-with-body --max-time 660 -sS http://127.0.0.1:8003/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2025-11-25' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"run_task","arguments":{"role":"chat","task":"Обязательно используй delegate_task: передай роли analyst вычисление 17 * 19, получи её ответ и сообщи результат и sessionId дочерней сессии."}}}'
```

Ожидается ответ `323` после фактического вызова `delegate_task`. Дочерняя
сессия видна через MCP `list_chats` и `get_chat`; её связь с родителем,
состояние задачи и результат сохраняются в PostgreSQL вместе с конфигурацией
роли. Состояния переходов также пишутся в логи API как `ax_delegation`.

При ошибке `delegate_task` возвращает `sessionId` и роль упавшего дочернего
агента, безопасную причину в `error` и диагностику `failure`: этап `stage`
(`worker_startup` — запуск AX, `worker_message` — выполнение запроса), код
`code` и тип исключения `error_type`. Эти поля сохраняются в сессии и логах
API. Например, `mcp_discovery_failed` означает сбой подключения MCP-инструментов
дочерней роли до вызова модели. Полный текст исключения в A2A-ответ не попадает.

```bash
bash compose.sh --env-file .env -f ax_local/compose.yaml logs --tail=500 api | grep '"event": "ax_delegation"'
```

Каждое делегирование создаёт новую сессию. Дочерний воркер завершается после
ответа или ошибки; при завершении хода родителя незавершённые потомки
отменяются. Повтор A2A-запроса с тем же `messageId` возвращает существующую
задачу. После перезапуска API прерванные задачи помечаются ошибкой и их
воркеры удаляются; повторный запуск работы требует новой задачи.

Дополнительный контекст передаётся явно в `task`: требования, текст, JSON или
патч. HTTP harness автоматически добавляет исходные запросы пользователя,
последний ответ родителя как непроверенный контекст и политику публикации.
Файлы workspace и результаты инструментов родителя не копируются; передавайте
нужные доказательства или доступную дочернему агенту ссылку на repository/ref/PR.
У `frontend_engineer` и `qa_engineer` по текущему `config/roles.json` нет
файловых и shell-инструментов: их ответы содержат предложения и сценарии,
а выполнение проверок требует отдельно настроенных инструментов роли.

Клиент worker и HTTP/JSON-RPC сервер используют официальный
[A2A Python SDK](https://github.com/a2aproject/a2a-python) `1.2.2`
с протоколом [A2A 1.0](https://a2a-protocol.org/latest/specification/).
Наш слой отвечает за роли, запуск AX, хранение сессий, лимиты и отмену;
SDK проверяет и сериализует протокольные сообщения и ошибки.
Поддерживаются `SendMessage` для текстовой задачи, `GetTask`,
`CancelTask`, Agent Card по `/a2a/ROLE/.well-known/agent-card.json` и текстовый
результат как Artifact. Клиент использует заголовок `A2A-Version: 1.0`
и `configuration.returnImmediately: true`, затем опрашивает `GetTask`.
При отсутствии `returnImmediately` сервер ждёт завершения задачи,
не блокируя остальные HTTP-запросы. Старое поле `blocking` не используется.
Streaming, push notifications, загрузка файлов и полный набор операций A2A
не реализованы. Токен делегирования действует только во время хода его
агента; он не сохраняется в PostgreSQL и не передаётся shell/MCP-процессам.

Docker-образы устанавливают SDK автоматически. Для локальных Python-проверок
установите `python3 -m pip install --group ax` из корня репозитория
(нужен pip 25.1 или новее). Версии Python-зависимостей всех образов и CI
задаются только в `pyproject.toml`.
Проверка реальных sandbox без вызова модели: скопируйте
`ax_local/tests/test_a2a_sdk_live.py` в `/tmp/test_a2a_sdk_live.py` контейнера API
и выполните `docker exec -e AX_TEST_SDK_LIVE=1 popot-ax-local-api-1 python /tmp/test_a2a_sdk_live.py`.

## Подготовка

Версии AX, Substrate, `ko`, `kubectl`, OmniRoute, Holmes, Cognee, PostgreSQL,
nginx и базовых образов Python/Go/Node задаются в одном файле
`pyproject.toml`, в секции `[tool.popot.build]`. Её читает
`ax_local/cluster/build_versions.py`; bootstrap и оба AX Dockerfile получают
от него проверенные shell-переменные, а проверки локальных патчей и Holmes — словарь.
Для Compose используйте `bash compose.sh --env-file .env -f ax_local/compose.yaml ...`:
обёртка загружает версии и передаёт образы в Dockerfile через именованные build contexts.
`up.sh`, bootstrap и `rebuild-worker.sh` делают это автоматически. Для ручного
`docker build` передайте `--build-context python-base=docker-image://<PYTHON_IMAGE>`
и `--build-context go-base=docker-image://<GO_IMAGE>` из этой секции.
При обновлении AX меняйте `AX_VERSION` и
`AX_COMMIT` вместе и проверяйте совместимость Substrate и наших патчей.

Нужны работающий Docker Desktop с BuildKit и Compose 2.17+, `git`, Go 1.27.1+,
`kubectl` и Python 3.11+.
Команда `python3` в текущем окружении должна запускать Python 3.11 или новее:
AX-скрипты используют встроенный `tomllib`. `up.sh` проверяет версию Python и
настройки сборки до запуска контейнеров. В Docker версии читает отдельный
этап сборки на Python 3.12; дополнительных Python-зависимостей для этого нет.
Для выбранного провайдера подготовьте его ключ в `.env`, если он требуется.
При отсутствии `ko` bootstrap установит версию из `KO_VERSION`
в `ax_local/.local/bin`; `kind` ставит скрипт Agent Substrate.
Первый запуск скачивает исходники и контейнерные образы и может занять время.

Из корня репозитория:

```bash
bash ax_local/up.sh
```

При первом запуске команда подготавливает локальный кластер, собирает worker и
поднимает PostgreSQL, API и MCP через Compose. При повторном запуске она
пересобирает worker, обновляет его в локальном registry и пересоздаёт API/MCP.
Используется `POPOT_DB_PASSWORD` из существующего `.env`. Все команды выполняются
через эту точку входа. Она также запускает остановленные локальные контейнеры
`kind-registry` и `popot-ax-control-plane` и выставляет таймаут
`atenet-router` из `ax.route_timeout_seconds` (по умолчанию 1920 секунд).
Для настройки роутера скрипт вызывает `kubectl` с явными путём к локальному
`ax_local/.local/kubeconfig` и контекстом `kind-popot-ax`; рабочий контекст
пользователя не меняется.

Для другого провайдера поменяйте `agent` нужной роли и заполните переменные
его профиля в `.env`. Например, `nous` использует `NOUS_MODEL` и `NOUS_API_KEY`,
а `nvidia_nim` — `NVIDIA_MODEL` и `NVIDIA_API_KEY`. Затем примените настройки:

```bash
bash ax_local/up.sh
```

Python-пакет на хосте устанавливать не нужно. Команда запуска сама готовит
kubeconfig для API-контейнера при первом
старте.

Ранее запущенный на хосте `python3 -m ax_local.server` можно остановить через
`Ctrl+C`: Compose запускает собственный API контейнер.

Bootstrap фиксирует AX на `v0.3.1`, Substrate — на commit из его `go.mod`,
строит runner под архитектуру машины и сохраняет digest образа в
`ax_local/.local/worker-image`. Он использует свой `KUBECONFIG` и готовит
копию для API контейнера. API контейнер подключается к Docker сети `kind` и
к Kubernetes API узла `popot-ax-control-plane`, без Docker socket. Если имя `popot-ax` или
`kind-registry` занято несовместимым локальным ресурсом, скрипт останавливается.
Состояние `.local/` игнорируется Git.

Прокси в API контейнере использует endpoint из профиля и принимает запросы
только с токеном текущего запуска. Для локального Ollama проверьте, что он
слушает адрес, доступный Docker контейнерам через `host.docker.internal`.

## Проверка

Проверьте контейнеры и вызов существующего MCP инструмента:

```bash
bash compose.sh --env-file .env -f ax_local/compose.yaml ps db api mcp-server
curl --fail-with-body -sS http://127.0.0.1:8003/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2025-11-25' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"run_task","arguments":{"role":"analyst","task":"Вычисли 17 * 19 через calculate."}}}'
```

Логи API и MCP при проверке:

```bash
bash compose.sh --env-file .env -f ax_local/compose.yaml logs -f api mcp-server
```

Таймаут одного запроса к модели задаётся в
`config/runtime.json → timeouts.model_request_seconds` (120 секунд по умолчанию).
AX-прокси вычитает `proxy.response_margin_seconds` из `ax_local/config.json`
(5 секунд, но не больше половины лимита), чтобы успеть вернуть HTTP 504 раньше,
чем worker закроет соединение. Это socket timeout, а не гарантия общего времени
всего ответа. Если остаток времени хода меньше, worker может завершиться раньше.
При таймауте провайдера в логах API появляется `model_upstream_timeout` с моделью,
лимитом и временем ожидания; при таймауте в harness — `model_timeout` с номером
раунда. Закрытое клиентом соединение обрабатывается без traceback BrokenPipe.
`config/runtime.json → model.request_retries` задаёт число повторов запроса
к модели при socket timeout или HTTP 502/503/504: целое неотрицательное число,
0 отключает повторы. Поле обязательно; текущее значение 10 разрешает
до десяти повторов после первой попытки, если хватает общего времени хода.
Повторяется только текущая генерация с той же историей и результатами инструментов,
в пределах оставшегося времени хода. Выполненные вызовы инструментов не запускаются
повторно этим механизмом; таймаут самого инструмента завершает ход.
В логах видны `attempt` и `model_retry`. Повтор генерации может дополнительно
тарифицироваться провайдером. HTTP 401/403 повторно не запрашиваются.
После изменения конфигурации/кода примените `bash ax_local/up.sh`.

Первый `run_task` ждёт готовности AX Task до `ax.startup_timeout_seconds` из
`config/runtime.json`; `curl` до ответа ничего не выводит. Если ожидание
затянулось, проверяйте фазу Task в другом терминале, пока запрос выполняется:

```bash
bash compose.sh --env-file .env -f ax_local/compose.yaml exec -T api \
  ax --context=kind-popot-ax --atespace=ate-demo-counter get tasks
bash compose.sh --env-file .env -f ax_local/compose.yaml logs --since=10m api \
  | rg 'AX task|POST /tasks'
```

После ошибки API удаляет AX Task, поэтому поздний `get tasks` может вернуть
пустой список. В сообщении об ошибке и логах API остаются последняя фаза и
причина из статуса AX; исходные значения окружения Task не выводятся.

Подключение клиентов:

```bash
codex mcp add popot-ax --url http://127.0.0.1:8003/mcp
claude mcp add --transport http popot-ax http://127.0.0.1:8003/mcp
```

MCP инструменты: `run_task`, `send_message`, `list_chats` и `get_chat`.
Сохраните `sessionId` из ответа для продолжения и восстановления чата.
Поле `container` в AX ответе содержит имя AX Task; `workspace` будет `null`,
потому что AX workspace находится внутри actor.
После смены профиля роли создавайте новый чат: существующие сессии сохраняют
прежний `agent` и конфигурацию роли. Если прежний профиль больше не используется
ни одной ролью, API сообщает, что профиль сохранённой сессии недоступен.

## Восстановление сессии после ошибки очистки workspace

Если API сообщает `Timed out deleting previous AX task`, а контроллер сначала
сообщил `permission denied` при удалении `durable-dir`, затем `runsc state:
exit status 128`, примените локальное исправление для закреплённой версии
Substrate:

```bash
python3 ax_local/cluster/substrate_cleanup.py --apply
```

Без `--apply` команда только выводит описание изменений. При применении она
проверяет отдельный kubeconfig, настроенный kind-контекст и commit Substrate,
добавляет патч в локальный checkout, запускает тест helper, собирает Linux-образ
`atelet` через локальный `ko` и обновляет существующий DaemonSet в `ate-system`.
Сборка или тест с ошибкой останавливают процесс до изменения DaemonSet.

Изменения затрагивают службу очистки `atelet`: ей добавляются файловые
capabilities `DAC_OVERRIDE` и `FOWNER` для удаления каталогов другого UID,
включая вложенные каталоги со sticky bit. Это расширяет доступ `atelet` к
смонтированным файлам; capabilities worker/агентов не меняются. Патч повторной
очистки действует только для gVisor: если bundle и runsc-state существуют и
уже пусты после предыдущего `resetActorDirs`, повторный TerminateWorkload
пропускается и очистка durable-dir продолжается. Ошибки чтения каталогов
останавливают очистку, а не считаются успешным завершением.

После успешного rollout повторите исходный запрос **с тем же `sessionId`**.
API повторно запросит удаление старой Task, создаст worker и восстановит
сохранённую историю из PostgreSQL. Содержимое удаляемого workspace не
восстанавливается из истории. Скрипт не меняет записи сессий и не запускает
повторно пользовательскую задачу самостоятельно.

Это отдельный локальный патч, не обновление upstream Substrate. `ax_local/up.sh`
применяет его автоматически после bootstrap или запуска существующего
kind-кластера, до запуска API. При ошибке установки исправления запуск
останавливается. Повторный upstream deploy `atelet` может заменить образ
или capabilities; следующий `up.sh` обнаружит это и применит исправление снова.

После успешного rollout скрипт сохраняет версию патча и digest образа в
`.local/substrate-cleanup.json`. При следующем запуске он сверяет эти данные
с текущим DaemonSet, проверяет capabilities и ждёт готовности rollout.
Если исправление уже установлено, сборка и обновление DaemonSet пропускаются.
После установки старой версией скрипта без этого файла первый запуск выполнит
сборку ещё раз и создаст отметку для последующих проверок.

## Ограничения локального запуска

- Адаптер вызывает `ax ssh` для каждого сообщения. Для длинной истории он
  передаёт запрос несколькими частями, так как AX v0.3.1 не пересылает stdin
  в `ax ssh`. Это проверяет AX Task lifecycle, но добавляет накладные расходы
  CLI и туннеля к задержке ответа.
- После ответа пользовательская сессия приостанавливается. Через два часа
  без продолжения API удаляет AX Task; следующий запрос восстанавливает историю
  из PostgreSQL в новом worker. После удаления Task файлы AX workspace не
  восстанавливаются. Явное удаление чата также удаляет его историю.
- Если удаление старой Task не завершилось, восстановление сессии ждёт его
  в пределах `ax.cli_timeout_seconds` (для делегирования также действует
  оставшийся бюджет родителя). Таймаут этого этапа возвращается как HTTP 502
  с `Timed out deleting previous AX task`, до запуска worker и обращения к
  модели. Неудачная очистка после idle timeout пишет
  `AX task cleanup not confirmed` в лог API. Проверяйте статус Task и лог
  `deployment/ax-controller` в `ax-system`: увеличение лимитов модели
  не устраняет ошибку удаления actor в Substrate.
- В используемой версии Substrate `atelet` работает как UID/GID 0 с
  `capabilities.drop: [ALL]`, а инструменты Popot создают файлы как UID/GID
  10001. Созданные `write_file` каталоги имеют режим `0770` до применения
  umask; очистка durable workspace через `os.RemoveAll` может получить
  `permission denied`. Actor к этому моменту уже остановлен. При повторном
  удалении очистка может упасть раньше на `runsc state` для отсутствующего
  sandbox. Для этого случая выше описан локальный патч `substrate_cleanup.py`;
  одна диагностика адаптера его не исправляет. Не удаляйте записи Task из хранилища вручную: это скроет
  незавершённую очистку ресурсов.
- Используется WorkerPool `popot-workers` в пространстве `ate-demo-counter`,
  созданный из совместимого demo-пула Agent Substrate. Кластер служит только
  для разработки.

Источники: [AX v0.3.1](https://github.com/google/ax/tree/v0.3.1),
[контракт runner](https://github.com/google/ax/blob/v0.3.1/docs/runner.md),
[локальный kind для Agent Substrate](https://github.com/agent-substrate/substrate/blob/main/README.md#quickstart-development).

The startup worker-health check also synchronizes Substrate WorkerPool CPU/RAM
from `task_resources` in `ax_local/config.json`. It waits for the replacement
pods and their registry entries before allowing tasks, so changing task resources
also updates the workers that host the gVisor sandboxes.

Code review turns inherit the shared 900-second budget (within the AX 1920-second route
timeout). The HTTP harness reserves up to `model.final_answer_reserve_seconds`
(currently 120 seconds) from `config/runtime.json` for a final answer, stops
new tools before that reserve, and returns an explicitly partial result if the
work budget expires. A final model timeout also returns a partial result; it
never repeats external writes. Partial turns are marked failed in Cognee and
are not captured as completed project knowledge. A missing response does not
undo already published GitHub reviews/comments; inspect them before retrying.

### HolmesGPT: диагностика AX в kind

Запуск по запросу из корня репозитория, после `bash ax_local/up.sh` и запуска
OmniRoute:

```bash
python3 -m ax_local.cluster.holmes "Почему перезапускаются AX workers? Проверь состояние, события и логи."
```

Команда запускает Kubernetes Job в `ax-diagnostics`, используя официальный образ
`robustadev/holmes` с версией `HOLMES_VERSION` из `pyproject.toml`. Постоянно работающий сервис и доступ к Docker socket
не требуются. Holmes использует свой цикл работы с инструментами; эта команда
пока вызывается из терминала, отдельной роли/MCP-инструмента в AX нет.
При первом запуске команда скачивает образ через Docker и импортирует его
в containerd локального kind-узла; последующие запуски используют этот кеш.
В pod Docker socket и административный kubeconfig хоста не передаются:
`kubectl` использует только токен своего ServiceAccount.

В корневом `.env` модель задаётся точным OmniRoute ID:

```dotenv
HOLMES_MODEL=nvidia/nvidia/nemotron-3-super-120b-a12b
```

Первый `nvidia/` — ID провайдера OmniRoute; оставшаяся часть — ID модели NVIDIA.
Holmes использует OpenAI-совместимый endpoint шлюза на
`http://host.docker.internal:20128/v1` и `OMNIROUTE_API_KEY` из `.env`.
Ключ передаётся через stdin в Kubernetes Secret, в аргументы команд и ConfigMap
не попадает. Платные/автоматические маршруты ограничены разрешениями этого ключа.
Выбран только Nemotron Super, без перехода на более слабые модели; недоступность
его dev-квоты может завершить расследование ошибкой. Основа выбора —
`reports/vps-models-20261018T122551Z/recommendations.json` и проверка tool calling;
отчёт измеряет надёжность и задержки, а не сравнительное качество SRE-расследований.

ServiceAccount `ax-diagnostics/holmes` получает только `get/list/watch` для
`pods`, `pods/log`, `events` в `ax-system`, `ate-system` и namespace `atespace`
из `ax_local/config.json` (сейчас `ate-demo-counter`). Граница доступа — namespace:
все pod внутри этих трёх namespace доступны. Чтение secrets, других namespace,
nodes, `exec` и изменения ресурсов не разрешены. Встроенные toolsets Holmes
не загружаются: доступны только четыре инструмента состояния, событий, текущих
и предыдущих логов pod. Prometheus, Docker Compose и production-кластеры
к этому запуску не подключены.

Цикл расследования ограничен 12 шагами и 4096 выходными токенами на запрос;
время жизни Job — 10 минут. Состояние и логи сохраняются
на сутки, затем Job удаляет Kubernetes TTL controller. `up.sh` не запускает
расследования автоматически. Namespace, RBAC, конфигурация и Secret создаются
повторяемо при каждом вызове; после удаления kind-кластера команда создаст их
заново из репозитория и локального `.env`.

Проверка ограничений:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest ax_local.tests.test_holmes
kubectl --kubeconfig=ax_local/.local/kubeconfig --context=kind-popot-ax auth can-i list pods -n ax-system --as=system:serviceaccount:ax-diagnostics:holmes
kubectl --kubeconfig=ax_local/.local/kubeconfig --context=kind-popot-ax auth can-i get secrets -n ax-system --as=system:serviceaccount:ax-diagnostics:holmes
```

Ожидается `yes` для pod и `no` для secrets. Изменение модели применяется к
следующему запуску команды.

### Мониторинг ресурсов локального кластера

`bash ax_local/up.sh` настраивает существующий Prometheus и запускает Grafana:
<http://127.0.0.1:3002/d/popot-resources>. Панель доступна локально без входа,
с правами просмотра. Можно выбирать namespace, pod, role, task и имя процесса.
Фильтр role ограничивает задачи и процессы sandbox; общие pod/контейнеры
показывают ресурсы инфраструктуры и фильтруются отдельно через namespace/pod.

Сверху показаны общие графики CPU (ядра) и памяти (working set) за выбранный
период. Линия `All pods` суммирует все pod, включая системные namespace;
`Nodes including system overhead` показывает полную нагрузку узлов, включая
процессы вне pod. Эти линии не складываются. Фильтры namespace/pod/role/task/process
не меняют общие графики, поэтому рост и снижение общей нагрузки всегда видны.

- CPU и working-set память pod/контейнеров собираются с kubelet/cAdvisor
  каждые 15 секунд; requests, limits и restarts — через kube-state-metrics.
- Внутри активного sandbox harness каждые 5 секунд читает `/proc` и отправляет
  CPU, RSS, virtual memory и число потоков каждого процесса в установленный
  OpenTelemetry Collector. В метрики входят роль, Task, PID и имя процесса; аргументы
  запуска, переменные окружения и содержимое файлов не собираются.
- При suspend сбор внутри sandbox останавливается. Текущие показатели исчезают
  с панели после 20 секунд без новых samples; история остаётся. Короткие процессы,
  завершившиеся между samples, могут не попасть в метрики. CPU 100% означает
  одно ядро; сумма RSS может повторно учитывать общие страницы памяти.
- Панели по ролям показывают CPU, сумму RSS процессов, активные задачи и число
  разных задач за выбранный период, включая завершённые и suspended. Список ролей
  строится из истории метрик выбранного периода. Метка role добавляется новым
  Task после обновления API и worker; старые samples без роли доступны при All,
  но задним числом роли им не присваиваются. `unassigned` означает Task без роли.
  Имя `popot-chat-<session_id>` используется для сессий любых ролей: это Task
  внутри общего worker pod, а не отдельная роль `chat` или новый pod.
- Prometheus хранит историю до 7 дней или 1 GB данных, в зависимости от того,
  какой предел будет достигнут первым. Prometheus и Grafana используют PVC;
  повторный `up.sh` и перезапуск pod сохраняют данные. Удаление kind-кластера
  удаляет и его локальные volumes. При первом включении существующий TSDB
  копируется на PVC с краткой остановкой записи только в Prometheus.

Отдельно установить/обновить мониторинг:
`python3 ax_local/cluster/resource_monitoring.py install`.
После перезагрузки компьютера `up.sh` снова запускает соединение с Grafana;
для запуска только соединения используйте
`python3 ax_local/cluster/resource_monitoring.py forward`.
Его лог: `ax_local/.local/resource-monitoring-forward.log`. Соединение слушает
только `127.0.0.1` и автоматически восстанавливается после замены pod Grafana.
Установщик проверяет локальный kind context; production-кластеры не поддерживает.

Изменения сборщика процессов попадают в новые Task после
`bash ax_local/rebuild-worker.sh`. Проверка без обращений к модели:
`AX_TEST_LIVE=1 python3 -m unittest ax_local.tests.test_resource_monitoring_live`.
