# Baseline HTTP harness

Опциональные живые прогоны AX с настоящей моделью. Runner и оценщик находятся
отдельно от runtime: они не меняют рабочие роли, основной API или harness.
Результаты проверяются по файлам, SHA-256 и наблюдаемым событиям. Фиксированная
модель-судья и самооценка агента дополняют объективные проверки отдельными оценками.

## Настройки

[config.json](config.json) содержит настройки:

- `services.phoenix` — параметры сервиса Phoenix.
- `x-providers` — управляемые провайдеры, модели и параметры запросов.
- `x-operator` — email и права сервисного пользователя оператора в Phoenix.
- `x-tracing` — постоянный экспорт обычных задач AX в проект `popot-runtime`.
- `x-scoring` — запрос самооценки и фиксированный провайдер/модель judge.
- `x-evals` — baseline, варианты моделей с точными параметрами запросов,
  общее число повторов, бюджеты workflow, лимит допуска корневых задач и
  HTTP-таймауты runner. Префикс `x-` — штатное расширение
  Compose: Docker пропускает эту секцию, runner читает и проверяет её.

`baseline` — имя записи из `variants`, например `flash-max`. Одиночный запуск
берёт модель и параметры из этой записи; отдельного поля модели по умолчанию нет.
`repetitions` применяется к каждому сценарию каждого варианта матрицы.
`--model`, `--parameters` и `--repetitions` переопределяют значения JSON для
конкретного запуска. Если передать только `--model`, параметры остаются от
baseline-варианта; для других параметров передайте также `--parameters`.
Допустимы 1–3 повтора. `request_timeout_seconds` должен превышать
`workflow.total_seconds`. Runner выполняет сценарии последовательно;
`max_concurrent` задаёт допуск сервера, не запускает сценарии параллельно.
После изменения JSON снова скопируйте `evals` в API-контейнер перед новым запуском.
В каталоге результата отдельный `config.json` сохраняет фактические настройки,
включая CLI-переопределения, снимки ролей и SHA-256 исходной конфигурации.

Набор сценариев задаётся в [cases.json](cases.json), `--case` выбирает поднабор.
Параметры выбранного варианта применяются ко всем участвующим eval-ролям,
включая делегатов. Права и инструменты берутся из исходных ролей,
настройки sandbox и WorkerPool —
из [../ax_local/config.json](../ax_local/config.json). Изоляция Cognee и
отключение Harness² остаются частью фиксированного протокола ниже.

Секции `x-baseline` и `x-experiments` объединены в `x-evals`: перенесите общие
настройки, `baseline` и `variants`, удалив дублирующее поле `model`. Старые секции
в рабочем JSON отклоняются с сообщением о миграции. В новых снимках результатов
настройки находятся в поле `evals`; исторические снимки с полем `baseline`
по-прежнему читаются при сравнении и импорте в Phoenix.

## Постоянные трейсы AX

`x-tracing.enabled` включает экспорт всех выполняемых root-задач, делегированных
ролей и cron без sampling и независимо от открытого клиента. Отдельный
`x-tracing.project` задаёт один постоянный проект для рабочих агентов.
Baseline использует свой API и сохраняет прежний отдельный импорт экспериментов.

Root и дочерние роли представлены `AGENT` spans, реальные вызовы native/MCP tools —
`TOOL`. `LLM` spans создаются в защищённом API-прокси по фактическому ответу
провайдера: модель, HTTP-статус и числовой usage, включая запросы памяти и Harness².
Отсутствующий usage остаётся неизвестным. Телеметрия `popot-telemetry-v2` сохраняет
`input.value`/`output.value`: фактический JSON запроса после подготовки контекста
(system/history, tool schemas, параметры) и ответ провайдера (текст, tool calls,
finish reason, usage и reasoning, если провайдер его возвращает). OpenInference
атрибуты сообщений дают удобное представление; полный envelope хранится в JSON.
Времена tools наблюдаются на стороне API; LLM длительность измеряется в прокси.

TOOL содержит фактические аргументы и результат, переданный модели, включая
ошибки, вывод команд и делегирование. AGENT содержит вход задачи, итоговый ответ
и outcome. События harness показывают retries, compaction с размерами контекста,
budget/final-result/recovery решения; `harness_started` фиксирует разрешённые
tools, настройки бюджетов и SHA-256 harness. Skills получают общий отпечаток
загруженного текста `popot.skills.prompt_sha256`; сам текст виден в LLM input.
Предыдущие блоки по 64 управляющих события сохраняются дочерними CHAIN spans
`Harness events`, остаток — на AGENT. Для анализа считайте оба вида событий.

Payload ограничен 1 MiB на сторону, детали одного управляющего события — 16 KiB.
`popot.input/output.truncated`, `.bytes`, `.sha256` показывают усечение, размер и
отпечаток payload после маскирования. Усечённый JSON остаётся валидным envelope с preview.
Индексированные сообщения ограничены 32 сообщениями и 16000 символами на поле.
Phoenix сохраняет содержимое задач, инструментов и ответов. Распознаваемые секреты
маскируются перед экспортом и вычислением SHA-256. Ограничьте доступ к хранилищу:
пользовательский текст может содержать конфиденциальные данные.

Токены относятся к LLM-запросу. Точный расход на отдельный tool или skill
провайдер не сообщает: результат tool увеличивает последующий контекст, а один
LLM-ответ может вызвать несколько tools. Стоимость и TTFT не выдумываются.
Старые traces сохраняются; отсутствующие тела запросов восстановить из usage нельзя.

Phoenix Session объединяет всю задачу: `session.id = popot.root_session_id`
у корневого агента, всех дочерних ролей и их LLM/TOOL spans.
ID конкретного агента сохраняется в `popot.agent_session_id`, а его родителя —
в `popot.parent_session_id`. Когда родитель уже завершён или API перезапущен,
дочерняя роль получает root ID из сохранённых метаданных делегирования.
Продолжения могут создавать новые traces; общий `session.id` собирает их в одну
Session. Это группировка диалога с данным root ID; новый root ID создаёт другую Session.
Старые spans автоматически не перегруппировываются.

Атрибуты `popot.role` и `popot.agent_profile` различают роли и профили.
`popot.skills.configured` показывает конфигурацию роли; `popot.skills.loaded` — инструкции, загрузку
которых подтвердил worker. Успешный `read_file` по пути выбранного skill получает
`popot.skill.reference_read`. Skills — инструкции: эти метки не доказывают
выполнение моделью всех требований skill. Новая сессия после rebuild получает
актуальную загрузку skills; старые worker могут не отправлять эту метку.

В Phoenix откройте Projects → `popot-runtime` → Sessions и выберите root ID,
чтобы увидеть все traces задачи. Traces покажет иерархию ролей и вызовов,
Dashboard — стандартные графики latency, ошибок, LLM/tools и токенов.
Spans по умолчанию использует фильтр `parent_id is None`. Для наблюдения за
работающими агентами очистите его: AGENT span отправляется после завершения роли,
а закрытые LLM/TOOL spans поступают во время её работы и уже относятся к общей Session.
Это не таблица CODE evaluations baseline. Специализированные графики по skills
не создаются автоматически; их имена доступны в атрибутах spans.

Роль `project_operator` читает Phoenix напрямую из worker через встроенный MCP
`/mcp` с отдельным пользовательским ключом `MEMBER` в `PHOENIX_API_KEY`.
При недоступном Phoenix или отсутствующем ключе роль продолжает работу с другими инструментами.
Ей доступны изучение GraphQL-схемы и выполнение запросов чтения. Сервис работает
с `PHOENIX_ENABLE_MCP_CODE_MODE=false`, чтобы роль выбирала отдельные инструменты.
Настройка и правила анализа описаны в [AX operations](../ax_local/README.md#project-operator-единая-роль-для-анализа-проекта).

Секрет берётся из корневого `.env` по имени `x-tracing.api_key_env`; он остаётся
в API-контейнере. Из API Phoenix доступен через `x-tracing.endpoint`.
Сетевая отправка идёт отдельным потоком. Закрытые spans сначала сохраняются
в `x-tracing.outbox_directory`, named volume `phoenix-outbox`. После ошибки
отправка повторяется через `retry_seconds`; очередь переживает перезапуск API.
Не удаляйте volume при пересоздании контейнеров. Повтор после потерянного ACK
не создаёт второй span. Невозможность записи на диск отмечается событием
`phoenix_export_failed`; работа агента продолжается. Незавершённые spans при
аварийном завершении процесса не восстанавливаются из памяти.

Применить код и настройки:

```bash
bash evals/up.sh
bash ax_local/rebuild-worker.sh
```

Ошибки доставки видны в логах API как `phoenix_export_failed` без payload и ключей.
Очередь содержит маскированный payload и метаданные; файлы создаются с правами `0600`.
Controlled evals пишут такие же proxy spans в `baseline/model-spans.jsonl` (`0600`),
затем импортируют их в Phoenix вместе с событиями worker. Request ID связывает
HTTP-вызов с gateway receipts: совпавшие gateway LLM spans не дублируются,
расход внутренних попыток берётся из квитанций шлюза. Пропуски остаются неизвестными.
`llm_requests` считает попытки harness. Квитанции внутренних повторов gateway учитываются в расходе токенов.
Все агенты eval-задачи используют общий root `session.id`, как обычные задачи.
Служебный MCP discovery содержит метаданные обнаружения, а не полный JSON-RPC
handshake. У независимого judge отдельный trace с оценкой, объяснением, моделью,
usage и отпечатком рубрики; его HTTP payload не проходит через AX proxy capture.
Внутренние вызовы внешних сервисов за границей tool не трассируются автоматически.

## Протокол

- По умолчанию шесть сценариев из [cases.json](cases.json), по два повтора, последовательно.
- По умолчанию выбран вариант `flash-max`: прямой маршрут
  `ollama-cloud/deepseek-v4.1-flash:1017`, параметры из его записи `variants`.
- Контролируемый локальный набор инструментов: native tools, локальный Git
  и разрешённое делегирование. GitHub/Fetch/Context7 MCP исключены из
  экспериментальных снимков: исходный пробный запуск остановился на недоступном
  GitHub discovery до первого LLM-запроса. Harness² выключен для сравнения
  основных исполнителей без дополнительного оптимизатора.
- Cognee MCP и переменные `COGNEE_API_URL`/`COGNEE_PASSWORD` удалены из снимков
  всех ролей, включая дочерние. Это также выключает автоматические recall,
  capture и журнал Cognee. Новые `baseline-*` brains не создаются.
  Рабочие роли проекта сохраняют свою память. Метка `[project: baseline-...]`
  остаётся идентификатором сценария без обращения к Cognee.
- Workflow по умолчанию: 600 секунд, два coordination turns по 300 секунд, резерв проверки
  60 секунд. Используются штатные WorkerQueue/WorkerPool с лимитом из
  `ax_local/config.json`; одновременно выполняется один корневой сценарий.
- Не изменять harness или сценарии посередине измерения. Версии и SHA-256
  исходников, ролей, skills и конфигурации сохраняются в `config.json`.

Текущий протокол помечен `memory_mode: disabled` в конфигурации и Phoenix.
Исторический `baseline-20261111` выполнен с включённой памятью; его результаты
сохранены отдельно. Для сравнения harness используйте новую серию без памяти
на обоих исполнителях. Проверки самой памяти требуют отдельной серии с
изолированным хранилищем Cognee.

`passed` означает выполнение функциональных проверок и контракта outcome.
`functional_passed` показывает проверки результата отдельно от состояния
workflow. `false_completion` фиксирует `completed` при проваленной объективной
проверке. Ожидаемый `blocked` в сценарии отсутствующего задания — успех.
Все корректно измеренные прогоны, включая неудачи агентов, остаются в знаменателе.
При ошибке самого оценщика серия останавливается: исходный отчёт сохраняется,
незавершённые измерения учитываются отдельно. Пустые метрики не заменяются нулём.

## Выполнение

Все текущие наборы одной командой из корня проекта:

```bash
bash evals/run-all.sh
```

Нужны уже работающие AX API, OmniRoute, Phoenix и готовый worker image;
`.env` и провайдер модели выбранного `x-evals.baseline` должны быть настроены.
Launcher использует `docker`, `git` и `python3`. Он выполняет runtime-evals
по последним 12 часам с записью CODE-оценок, все шесть `cases.json` с настройками
`x-evals`, сбор gateway usage, построение отчёта и импорт эксперимента Phoenix.
Baseline запускает настоящих агентов и расходует квоту: при двух повторах
это 12 корневых сценариев плюс разрешённые ими делегаты. Runtime-evals новых
LLM-вызовов не создают. Проверки bootstrap провайдеров не входят в эти наборы.

Результат — `reports/evals/full-<UTC>/{runtime,baseline}/`; можно задать своё
новое имя: `bash evals/run-all.sh before-opencode`. Исходный HEAD помечается
`dirty`, если есть незакоммиченные изменения; оценщик сохраняет хеши фактических
исходников API-контейнера. Для сравнения сначала пересоберите runtime из нужного
checkout. При ошибке захвата baseline launcher сохраняет доступный частичный
результат и останавливается; автоматического повторения неудачных измерений нет.

`runtime/summary.md` содержит наблюдения runtime, `baseline/summary.md` —
объективные проверки сценариев; `baseline/phoenix.json` содержит URL эксперимента.
Это ручная команда; deploy автоматически полный benchmark не запускает.

### Сравнение моделей и параметров

```bash
python3 ax_local/cluster/resource_monitoring.py install-evals
python3 -m evals.matrix --output reports/evals/models-before-harness
```

Первая команда обновляет provisioning существующей Grafana, сохраняя её PVC и
ресурсный дашборд. Полный `resource_monitoring.py install` также устанавливает
дашборд evals при раскатке. Нового сервиса или exporter нет: runner отправляет
OTLP gauges в существующий Collector через ограниченный loopback `kubectl proxy`.
Нужен настроенный локальный kind-контекст; без мониторинга данные измерений
сохраняются, ошибка отправки явно записывается в `report.json → monitoring`.

Матрица запускает варианты `x-evals.variants` параллельно: `x-evals.parallel_models`
задаёт предел одновременно выполняемых вариантов (по умолчанию 3).
Внутри каждого варианта кейсы выполняются последовательно. Baseline включается
в первую группу; сравнение готового кандидата публикуется после завершения baseline.
Общее `x-evals.repetitions` задаёт число повторов каждого
сценария на каждом варианте; флаг `--repetitions` переопределяет его для матрицы.
Параметры варианта заменяют параметры всех eval-ролей,
включая делегатов; рабочие профили не меняются. По умолчанию это flash-max,
glm-max, mistral-max, minimax-max и nemotron-free: шесть сценариев × два повтора
× пять вариантов = 60 root-задач,
плюс делегаты и отдельный judge для каждого измерения. Runtime-аудит исторических
трейсов повторно для каждого варианта не запускается. Это платные/квотируемые
вызовы, если провайдер тарифицирует выбранную модель.

Предел можно переопределить флагом `--parallel-models`, например:

```bash
python3 -m evals.matrix --output reports/evals/parallel-models --parallel-models 3
```

Runner проверяет запас слотов: `параллельные модели × (max_depth + 1) + warm_workers`
должен укладываться в `max_workers`. При текущих значениях `3 × 3 + 3 = 12 ≤ 14`.
Реальные воркеры берутся из общего AX WorkerPool; его контроллеры учитывают
назначенные акторы других runner и расширяют пул по спросу. Это расчёт резерва,
а не гарантия скорости: квоты провайдера и конкуренция за CPU/память влияют на замеры.
Условия записаны в `config.json → evals.parallel_models`, metadata Phoenix и
колонке «Параллельных моделей» в Grafana. Сравнение сохраняет их в `parameter_changes`.
Для сравнения задержек с прежними последовательными запусками используйте
`--parallel-models 1` или учитывайте изменение условий нагрузки.

Каждый вариант получает отдельную копию кода evals, proxy, сессии, capture и
журнал публикации. При старте матрица сохраняет исходники и launchers в
`.launcher/evals/`; все варианты используют эту неизменяемую копию. Shell также
фиксирует тело скрипта в памяти перед выполнением длительных команд: последующее
редактирование рабочего checkout не меняет выполняющийся launcher.
Консоль печатает старт и завершение вариантов; подробный
вывод находится в `<variant>.log` рядом с `matrix.json`. Один координатор
записывает общий manifest. Ошибка одного варианта сохраняется в `failures`;
остальные варианты продолжают выполнение, а итоговая команда возвращает ошибку.
При Ctrl+C новые варианты не стартуют. Уже запущенные завершают текущий кейс
и освобождают свои sandbox; launcher изолирован от сигнала терминала, координатор
ждёт его завершения. Один workflow ограничен 600s, `session_resume` содержит два
последовательных workflow, затем вызывается judge (до 90s). Это отмена между
кейсами, а не мгновенное прерывание запроса. Частичный capture сохраняется.
Сбой записи cancel marker явно указан в `cancel_errors`.

`glm-max` использует `ollama-cloud/glm-5.3-flash`, `mistral-max` —
`ollama-cloud/mistral-large-4`, `minimax-max` — `ollama-cloud/minimax-m3.1-flash`.
Все три задают `reasoning_effort=max` и
`max_tokens=65536`, как baseline `flash-max`. Прямые маршруты внесены в
`apiKey.permissions.allowedModels` deploy-конфига OmniRoute и каталог Ollama Cloud
в Phoenix; production fallback-комбо задаётся отдельно.
`nemotron-free` использует прямой
маршрут `nvidia/nvidia/nemotron-3.5-lightning-30b-a3b` в рамках доступа NVIDIA NIM
для разработки/тестирования; фактическая квота зависит от аккаунта.
Для него задан `max_tokens=64000`, reasoning — по умолчанию провайдера,
без `reasoning_effort`; интерфейс показывает `default`. Это разные настройки моделей,
а не сравнение при идентичном reasoning. Независимый judge остаётся прежним.

Короткая проверка связки на двух моделях:

```bash
python3 -m evals.matrix --output reports/evals/models-smoke --variant glm-max --variant mistral-max --baseline glm-max --case honest_blocker --repetitions 1
```

Каталог должен быть новым. Можно повторять `--case`, выбирать `--variant` и
переопределять `--baseline`, сохраняя его среди выбранных вариантов. Один запуск
тоже принимает флаги: `bash evals/run-all.sh flash-low-check --model ollama-cloud/deepseek-v4.1-flash:1017 --parameters '{"max_tokens":65536,"reasoning_effort":"low"}'`.

При сбое матрица записывает `status: failed`, вариант, тип ошибки и код выхода
в `matrix.json`. Продолжить ту же матрицу с теми же параметрами:

```bash
python3 -m evals.matrix --output reports/evals/models-before-harness --resume
```

Завершённые измерения повторно не запускаются: runner продолжает публикацию из
сохранённого `baseline/`, затем запускает ещё не измеренные варианты. При
незавершённом capture он останавливается, чтобы не повторять обращения к модели
незаметно для пользователя. Параллельное продолжение одной папки блокируется.
Для старой матрицы, созданной до введения параллельности, добавьте к `--resume`
флаг `--parallel-models 1`. Изменять режим нагрузки посреди матрицы runner не позволяет.

В [Grafana Evals](http://127.0.0.1:3002/d/popot-evals) выберите набор задач,
эксперименты и baseline. Видны план/завершённые кейсы, средние токены входа/выхода,
длительность, LLM-запросы, шаги, retries, tools, ошибки LLM/tools/формата,
coordination turns и оценки. Прогресс обновляется после завершения кейса и judge;
открытый запрос внутри кейса не считается завершённым. Токены присоединяются из
gateway после варианта, затем импортируются подробные Experiments/traces Phoenix.
Запуск появляется в списке Grafana сразу по метрикам прогресса, даже если импорт
Phoenix ещё не начался или завершился ошибкой. Трейсы Phoenix публикуются после
всех кейсов варианта модели; потокового показа текущего запроса в этом runner нет.
Таблица параметров содержит ссылку на Phoenix, модель, harness, параметры и ревизию.
Панели сгруппированы в сворачиваемые разделы: обзор запуска, качество результата,
оценки judge и агента, токены, время выполнения, действия harness, ошибки и повторы,
параметры и ссылки. Исходное значение метрики и её Δ расположены рядом.
История gauges ограничена retention существующего Prometheus.

Объективный успех и judge: больше — лучше. Затраты, ошибки и false completion:
меньше — лучше. Панели Δ уже меняют знак для MINIMIZE, поэтому зелёное Δ > 0
всегда означает улучшение этой метрики. Заголовки исходных значений указывают
направление, а подсказки Δ содержат формулу: `baseline − эксперимент` для затрат
и ошибок, `эксперимент − baseline` для качества. Например, 1000 → 800 токенов
даёт +200 улучшения. Это абсолютная разница, для долей — процентные пункты.
`project_operator` получает эти правила через `operations/runtime-evals` и
анализирует данные дашборда через ограниченные запросы `project_inspect(kind=metrics)`;
его инструменты запускают runtime evals, полный benchmark запускается на хосте.
Падение качества вместе с экономией даёт
«КОМПРОМИСС». Ошибки tools включают ожидаемые отказы сценария honest_blocker:
их число само по себе не устанавливает регрессию. Это наблюдаемые различия,
не доказанная статистическая значимость; один кейс/повтор проверяет проводку.

`objective_score` опирается на проверки runner. `judge_score` — отдельная модель
из `x-scoring`, одна и та же для всех вариантов, с версионированной рубрикой и
проверками/ответом в контексте. Её токены и trace отделены от расхода агента.
`self_score` берётся из проверенного `self-evaluation.json`: это самоотчёт,
повышение уверенности не окрашивается как улучшение качества. Недостающая или
невалидная оценка остаётся неизвестной. Модель judge может ошибаться; объективные
проверки она не заменяет. Самооценка не передаётся judge.

Протокол `popot-evals-v2` передаёт judge исходное задание и follow-up вместе:
итоговые артефакты оцениваются по последней фазе. В контекст входят объективные
проверки, нерешённые требования и метаданные артефактов с проверенным SHA-256.
Самооценка получает те же критерии: ожидаемый честный blocker считается успехом,
восстановленная ошибка инструмента — историческим evidence. Версия рубрики
входит в fingerprint; оценки разных версий автоматически не сравниваются.

Пересчитать только judge для сохранённого завершённого прогона можно внутри
API-контейнера после копирования актуального `evals`:

```bash
docker exec -i popot-ax-local-api-1 python -m evals.regrade /tmp/baseline-original --output /tmp/baseline-judge-v2
```

Команда использует ключ `PHOENIX_API_KEY`, создаёт новый каталог для эксперимента
`<model>-<reasoning>-judge-v2-<run-id>-<Phoenix number>`. Исходные отчёты, самооценки, traces и результаты задач
сохраняются. Новые вызовы делает только judge; агенты повторно не запускаются.
После копирования результата импортируйте его обычной командой `evals.phoenix`.
В metadata нового эксперимента сохраняются источник и хеши пересчёта. Старые
оценки judge v1 для `session_resume` учитывали только первую фазу и не подходят
для ранжирования моделей. Исторический неизвестный usage пересчёт не заполняет.

В Phoenix метрики `popot.eval.*` имеют направления MAXIMIZE/MINIMIZE/NONE,
а эксперимент baseline закрепляется штатным API. В его Compare можно раскрывать
отдельные кейсы и переходить к trace. При неизвестной оценке учитывайте error count:
нативный Phoenix может усреднять только известные значения. Сравнение runner и
Grafana строже: среднее метрики неизвестно при любом пропуске в серии.

Матрица сохраняет `matrix.json`, отчёты каждого варианта и
`<variant>/baseline/comparison.{json,md}`. Для сравнения с прошлым запуском:

```bash
python3 -m evals.compare reports/evals/previous/flash-max/baseline reports/evals/current/flash-max/baseline --publish
```

Сравнение требует одинаковых хешей задач, memory mode и пар case/repetition,
завершённого захвата и подтверждения модели через gateway. Ошибка runner или
неполная серия блокирует вывод «лучше». Изменение judge делает только его оценку
несопоставимой; версии harness/образа/параметров сохраняются как различия условий.
Уточнение заданий или инструкции самооценки меняет хеш набора и создаёт отдельную
серию/dataset: такой запуск не является чистым A/B тестом модели против старого набора.
Неизвестный usage не становится нулём; процент относительно нулевого baseline
не вычисляется. Полный benchmark при deploy автоматически не запускается.

Итоговое имя в Phoenix и Grafana: `<model>-<reasoning>-evals-<run-id>-<Phoenix number>`;
копия с новым judge — `<model>-<reasoning>-judge-v2-<run-id>-<Phoenix number>`.
Например, `deepseek-v4.1-flash:1017-max-evals-20261113T143602-9a12d9-30`.
`run-id` содержит дату и время старта матрицы в UTC и её короткий ID; он общий
для всех вариантов этой матрицы. Повторный импорт сохраняет этот ID. Для новых
экспериментов он также записывается в metadata `run_id`.
Номер появляется после создания эксперимента; до импорта используется временное
имя с ID запуска. Финальное имя и URL сохраняются в `phoenix.json`.
Исторические ключи Prometheus и frozen config сохраняются: `popot_eval_info.display_name`
связывает их с именем Phoenix. После переименования Grafana выбирает последнюю
подпись по `display_name_updated_at_seconds`, чтобы исторические labels не
дублировали эксперимент и не меняли значения метрик. В Grafana [именованные text/value группы](https://grafana.com/docs/grafana/latest/visualizations/dashboards/variables/advanced-variables/)
показывают это имя, сохраняя исходное значение фильтра и работоспособность старых ссылок.
«Набор задач» показывает имя dataset Phoenix и дату его создания в UTC:
`popot-harness-local-782a0561684e · 2026-11-12 23:39:00 UTC`.
Один dataset объединяет несколько моделей и запусков, поэтому дата относится
к dataset, а не к отдельному эксперименту. Поле `series_display_name` сохраняется
в `phoenix.json` и метриках info; значением фильтра остаётся прежний `series`.
До импорта или при отсутствии метаданных dataset в Phoenix доступно имя без даты.

Нужен уже работающий локальный AX и доступ к указанной модели через OmniRoute.
Команды выполняются из корня проекта. Идентификатор каталога должен быть новым.

```bash
docker exec popot-ax-local-api-1 python -c "from pathlib import Path; Path('/app/evals').mkdir(exist_ok=True)"
docker cp evals/. popot-ax-local-api-1:/app/evals/
git rev-parse HEAD
docker exec -i popot-ax-local-api-1 python -u -m evals.baseline --output /tmp/baseline-unique-id --repetitions 2 --source-revision <HEAD_FROM_PREVIOUS_COMMAND>
docker cp popot-ax-local-api-1:/tmp/baseline-unique-id reports/evals/
```

Прогоны создают собственный API/proxy/A2A процесс с отдельным файловым session
store. Worker удаляются после сохранения результатов. `sessions/` и JSONL
сохраняют доказательства дочерних результатов и восстановления.
Остановленный или неудачный запуск не переигрывается автоматически.
Для продолжения после устранения ошибки сбора используйте новый каталог,
`--repetition-start` и повторяемый `--case`, сохранив исходный batch и причину
исключения измерения. Не заменяйте реальные неудачи агентов удачными повторами.
Точные wire-кадры сохраняются в приватных `*.wire.ndjson` с правами `0600`;
JSONL для анализа исключает reasoning и маскирует известные секреты в полях событий.

### Метрики шлюза

```bash
docker cp evals/gateway.mjs popot-ax-local-omniroute-1:/tmp/baseline-gateway.mjs
docker cp reports/evals/baseline-unique-id/report.json popot-ax-local-omniroute-1:/tmp/baseline-report.json
docker exec popot-ax-local-omniroute-1 node /tmp/baseline-gateway.mjs /tmp/baseline-report.json > reports/evals/baseline-unique-id/gateway.json
python3 -m evals.report reports/evals/baseline-unique-id reports/evals/baseline-unique-id/gateway.json
```

Экспортируются только вызовы с root session ID данного baseline. Коллектор не
выгружает заголовки, запросы и ответы. Токены берутся из фактического usage;
`tokens_known` — сумма найденного usage, `tokens` остаётся неизвестным при
ошибке или незавершённом model request. Это учёт наблюдаемого расхода, не счёт
провайдера. Неизвестная стоимость остаётся неизвестной. `summary.md` разделяет
функциональные проверки и завершение workflow.

Новые model attempts имеют `request_id`, который передаётся через API-прокси
в записи gateway. Полнота расхода проверяется по совпадению попыток и квитанций
шлюза; ответ, пришедший после дедлайна turn, всё равно учитывается при наличии
usage. `usage_audit` показывает метод и число отсутствующих квитанций.
Для старых captures без ID остаётся консервативная проверка событий.
Генератор выбирает ID попытки, который проходит фильтр секретов без изменения. Суммы входных и выходных
токенов также остаются неизвестными, если захват запросов неполон.
В старых экспериментах суммы входных/выходных токенов при неизвестном полном
usage могли включать только известные вызовы; это ограничение исторических
метрик, а не доказательство экономии. Новые серии применяют строгую проверку.

Для локального `code_fix` родитель передаёт QA/reviewer Git bundle исходного
коммита: пересоздание коммита из вставленного текста не подтверждает ту же
ревизию. Независимые проверки также покрывают типы аргументов, границы страницы,
возврат нового списка и сохранность исходных данных. Workflow считает
`max_no_progress` числом последовательных turn без новых наблюдений; первый
checkpoint и turn с новыми результатами обнуляют этот счётчик.

## Оценки накопленных runtime traces

[runtime.py](runtime.py) собирает закрытые spans проекта `popot-runtime` за
фиксированное окно, сохраняет снимок и считает метрики без запуска агентов и
модели-судьи. Это baseline наблюдаемого runtime перед сменой harness;
контролируемые сценарии из `cases.json` по-прежнему нужны для оценки качества.

Роль `project_operator` запускает этот же оценщик напрямую из своего worker
через `mcp__evals__run_runtime_evals`, читает сохранённые разделы через
`mcp__evals__read_eval_report`. Она использует собственный `PHOENIX_API_KEY`:
MEMBER позволяет публиковать CODE-аннотации, `publish=false` допускает VIEWER.
Административный ключ в worker не передаётся. Встроенный Phoenix MCP остаётся
прямым интерфейсом запросов чтения. Endpoint/project берётся из `x-tracing`,
окно ограничено 7 днями, захват — 20000 spans и 90 секундами.
Отчёт передаётся нативными артефактами; большой JSON сжат в `.json.gz`, снимок
остаётся в workspace. При повторном запуске артефакты отражают последний run,
предыдущие run_id доступны этой же сессии. Полный host benchmark оператор
сам не запускает: его worker не имеет Docker socket или shell.
Повтор запроса с тем же явным `end`, окном и версией оценщика использует
сохранённый снимок; подтверждённая публикация не повторяется. При сбое записи
возвращается run_id с `status=failed_or_unknown` и неизвестным числом записей:
отчёт можно читать, а публикацию того же снимка безопасно повторить.

Запуск в существующем контейнере Phoenix использует установленный Python,
readonly bind каталога `evals` и уже настроенный административный ключ:

```bash
docker exec -w /opt/popot popot-evals-phoenix-1 python -m evals.runtime --output /tmp/runtime-before-harness-unique --hours 12 --annotate --api-key-env PHOENIX_ADMIN_SECRET
docker cp popot-evals-phoenix-1:/tmp/runtime-before-harness-unique reports/evals/
```

Без `--annotate` обращения к Phoenix только читают данные; достаточно
`PHOENIX_API_KEY` с ролью `VIEWER`. Ключ передаётся через окружение, не аргументом.
Можно задать `--project UHJvamVjdDo0`, `--endpoint` и timezone-aware `--end`.
Без `--end` конец окна фиксируется один раз перед первой страницей.
Выгружаются все виды spans без фильтра `parent_id`; обход всех страниц
останавливается с ошибкой при повторении cursor.

Результаты:

- `snapshot.json`: разрешённые метаданные, время окна, источник и SHA-256 оценщика.
- `report.json`: p50/p95/p99 с размером выборки, LLM/tool вызовы и ошибки,
  usage coverage, известные токены, разбивка по видам, ролям, моделям,
  инструментам и root sessions, сохранённые event counters и аудит полноты.
- `summary.md`: краткая сводка и ограничения измерения.
- `annotations.json`: квитанция записи CODE-оценок при `--annotate`.

CODE-оценки видны непосредственно у spans исходного проекта:

| Оценка | Что измеряет |
|---|---|
| `harness.runtime_ok` | Статус span `OK` / `ERROR`; это успех транспорта, не тестов задачи |
| `harness.duration_seconds` | Наблюдаемая длительность закрытого span |
| `harness.session_link_ok` | Совпадает ли Phoenix Session с root session ID |
| `harness.agent_identity_present` | Есть ли ID агента, включая legacy `metadata.session_id` |
| `harness.usage_complete` | Есть ли три неотрицательных числовых счётчика usage у LLM |
| `harness.model_identified` | Записано ли имя модели ответа |
| `harness.tokens_prompt`, `harness.tokens_completion`, `harness.tokens_total` | Фактически наблюдаемые токены LLM |
| `harness.tool_finished` | Tool span не помечен `popot.incomplete`; exit code команды этим не проверяется |
| `harness.declared_completed` | Агент сообщил `completed`; корректность результата этим не доказана |

Неизвестный usage не получает нулевую оценку расхода: сумма доступного usage
сохраняется как `tokens_known`, полный `tokens` остаётся `null`, если хотя бы у
одного LLM span нет total usage. Стоимость, functional success и false
completion остаются `null`: текущий экспорт не содержит необходимых доказательств.
Legacy exporter хранил только последние 64 события агента; v2 учитывает также
блоки `Harness events`. Audit показывает отсутствующий input/output, усечения и
число блоков. Ошибки ожидаемого восстановления нельзя объявлять регрессией
по одному счётчику `ERROR`.

Оценки используют identifier `harness-baseline-v1`; повторная запись той же
пары span/name обновляет её штатным upsert Phoenix. Другие annotations и исходные
spans не меняются. Незавершённая запись может быть повторена по снимку:

```bash
python3 -m evals.runtime --input reports/evals/runtime-before-harness-unique/snapshot.json --output reports/evals/runtime-recomputed-unique
```

Пересчёт без `--annotate` работает офлайн и не требует ключей. Снимки и отчёты
не содержат input/output, reasoning, tool arguments/results или произвольных
metadata. Старый `metadata.session_id` используется только для аналитики;
историческая группировка Sessions в Phoenix при этом не переписывается.
У агента и его потомков длительности пересекаются: их сумма не является
длительностью задачи. `observed_wall_seconds` — интервал между первым и последним
наблюдаемыми spans группы, а не доказанное полное время workflow.

Для сравнения с новым harness сохраняйте тот же набор сценариев, фактическую
модель и провайдера без fallback, параметры модели, роли, prompts/skills, режим
памяти, бюджеты, worker image и ревизию runtime. Текущие рабочие traces не
содержат весь этот provenance. Исторические рабочие задачи с разным составом
не доказывают выигрыш harness. Отсутствующий parent/root в окне может быть ещё
активен либо находиться за его границей; это само по себе не основание удаления.

## Phoenix

Образ Phoenix с версией и digest закреплён в
[../pyproject.toml](../pyproject.toml), `tool.popot.build.PHOENIX_IMAGE`.
Настройки сервиса находятся в [config.json](config.json): публикация порта,
авторизация, телеметрия и лимит памяти. [compose.yaml](compose.yaml) подключает
их штатным `extends`. Endpoint публикуется только на
`127.0.0.1:6006`; аутентификация включена, данные находятся в named volume.
Секреты хранятся в общем корневом `.env`, исключённом из Git, с правами `0600`.
Пример переменных — в [../.env.example](../.env.example). Требуются три разных случайных
значения: `PHOENIX_SECRET`, `PHOENIX_ADMIN_SECRET` и
`PHOENIX_DEFAULT_ADMIN_INITIAL_PASSWORD`.
Email для входа — `admin@localhost`, пароль — значение
`PHOENIX_DEFAULT_ADMIN_INITIAL_PASSWORD`. Для существующего хранилища изменение
initial password в `.env` не сбрасывает пароль пользователя.

```bash
bash evals/up.sh
bash evals/publish.sh reports/evals/models-before-harness/flash-max/baseline --baseline
```

`run-all.sh` автоматически вызывает `publish.sh`. Он использует отдельный
одноразовый контейнер `phoenix-import` из того же закреплённого образа с собственным
лимитом памяти 1 GiB; сервер Phoenix не делит этот лимит с импортёром. Capture
читается по строкам для текущего кейса, spans отправляются пакетами до 16.
Журнал `phoenix.json` записывается прямо в папку отчёта на хосте. Повторная
публикация сохраняет experiment/run IDs и продолжает недостающие оценки; новых
вызовов модели или judge нет. Ошибка импорта возвращает ненулевой код. Импорт
одной папки одновременно из двух процессов блокируется. Если журнал утрачен,
импортёр ищет существующий эксперимент по хешу замороженной конфигурации и
восстанавливает его runs по example, repetition и trace ID. Несовпадение этих
данных завершает импорт ошибкой.

`ax_local/up.sh` также запускает Phoenix и его bootstrap. В
`config.json → x-providers` заданы OpenRouter, NVIDIA NIM, Ollama Cloud и Nous:
имя подключения, endpoint, имя переменной ключа, `models` и необязательный
`extra_body`. Список моделей управляется этим JSON; это выбранные модели проекта,
а не автоматически загруженный полный каталог провайдера. Квоты и доступность
проверяются при выполнении запроса; bootstrap не запускает платную генерацию.

`up.sh` ждёт готовности сервера и запускает одноразовый `phoenix-init`, который
создаёт или обновляет подключения штатным GraphQL API и сверяет настройки и
списки моделей. `x-operator` задаёт email существующего сервисного пользователя
и роль MEMBER; bootstrap применяет и проверяет членство, сохраняя его API key.
На пустой базе сначала создайте этого пользователя и сохраните его ключ как
`PHOENIX_API_KEY`: статус `missing_user` явно сообщает об отсутствующем аккаунте.
ID сохраняются при повторной раскатке, ключи обновляются из
корневого `.env`; пользовательские подключения с другими именами не меняются.
Без ключа соответствующий провайдер пропускается с явным статусом. Это не
удаляет старое подключение. Ошибка bootstrap завершает запуск с ненулевым кодом.
Непосредственный `docker compose up` запускает сервер без регистрации подключений;
для полной раскатки используйте `bash evals/up.sh`.
Сервер пересоздаётся при запуске, чтобы загрузить свежий JSON. Данные в named
volume сохраняются; существующий AX exporter повторяет доставку из outbox.

`phoenix_server.py` перед запуском закреплённого Phoenix подключает две адаптации:
модели управляемых подключений берутся из `x-providers`, а параметры `extra_body`
добавляются к запросам соответствующего endpoint. Например, Nous получает
`tags` автоматически в Playground и серверном Chat Completions API. Явные
параметры запроса имеют приоритет. Шифрование ключей, права доступа, выполнение
запросов и закрытие клиентов остаются в Phoenix. При обновлении Phoenix нужно
проверить эти точки интеграции и повторить проверку раскатки с пустой базой.
Браузерное предпочтение Default Model bootstrap не изменяет.

Проверить bootstrap и адаптацию с пустой временной базой, повторной регистрацией
и короткой генерацией у всех четырёх провайдеров:

```bash
PHOENIX_TEST_PROVIDERS_LIVE=1 python3 -m pytest -q -s tests/test_phoenix_providers_live.py
```

Это opt-in проверка с реальными ключами из `.env`; вызовы учитываются в квотах
провайдеров. Основной набор тестов выполняется без этих обращений.

SDK уже установлен в закреплённом Phoenix image; зависимости рабочего
приложения не меняются. [phoenix.py](phoenix.py) сохраняет dataset version,
experiment, runs и CODE evaluations, связывая каждый прогон с trace ID.
`phoenix.json` — журнал успешного импорта; повторный вызов продолжает импорт,
не запускает агентов повторно. Конфигурация должна совпадать с журналом.
Для качества смотрите оценки `success`, `functional_success` и
`false_completion`: число successful runs в Phoenix означает успешную запись
результата эксперимента, включая измеренные неудачи агентов.
Расход токенов в CODE evaluations называется `total_tokens`: имя `tokens`
совпадает со встроенной колонкой Phoenix 21 и ломает List view сравнения.
Поле `tokens` в локальном отчёте и output прогона сохраняет прежнее имя.

Трейсы каждого эксперимента сохраняются в его собственный проект `Experiment-*`,
который Phoenix исключает из общего списка Projects. Пустой проект `default`
не содержит baseline. Открывайте связанный trace из результатов эксперимента.
Dashboard проекта показывает данные трейсов и их аннотаций; оценки `success`
и `functional_success` записаны как CODE evaluations эксперимента и доступны
в его сравнении, а не как аннотации spans на dashboard.

Spans восстанавливаются после выполнения: модельные запросы используют время,
usage и модель из OmniRoute; инструменты и сессии — время наблюдения API.
Границы незавершённых операций явно помечены. Исходные JSONL сохраняются.
Это не автоматическая OpenTelemetry-инструментация всех функций runtime.

## Проверки оценщика

```bash
python3 -m pytest -q tests/test_baseline.py
node --test tests/baseline-gateway.mjs
```

Контракт экспорта проверяется с SDK из закреплённого Phoenix image, без
обращений к модели, в отдельном контейнере:

```bash
bash compose.sh --env-file .env -f evals/compose.yaml run --rm --no-deps -T --volume "$PWD/tests:/tests:ro" phoenix-import -m unittest discover -s /tests -p test_phoenix_export.py -v
```

Небольшое число повторов даёт начальную точку сравнения, но не доказывает статистическое
превосходство модели или harness. Проверки внешнего GitHub, падения процесса
API, переключения моделей и публикации PR в этот набор не входят.
